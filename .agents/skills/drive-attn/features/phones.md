# Phones

A paired phone sees the agents, asks and Garden of one home profile and keeps
them current. The home dials out to its Cloud Relay in Attn Cloud and phones dial in, so
neither side needs an open port. Home and phone talk Noise end to end inside
the Cloud Relay's frames, so the Cloud sees only ciphertext. The phone talks to the
Home Gateway, an API apart from the app's `/ws` protocol that only grows, so
a phone from the App Store keeps working across home builds. Phone access is
experimental and off until the user turns it on.

The Cloud Relay contract is `docs/internal/cloud-relay-contract.md`, and
`internal/cloudlink/cloudrelaytest` holds any Cloud Relay to it. The
cloud link is `internal/cloudlink` (home keys in the data directory as
`cloud_sign_key`, `cloud_noise_key` and `cloud_home_id`), pairings are the
`phone_pairings` table, the daemon side is `internal/daemon/phones.go`, the
Home Gateway is `internal/daemon/home_gateway.go`, `home_gateway_asks.go`, `home_gateway_terminal.go` and `home_gateway_garden.go`, the phone
app is `mobile/`, the Home Gateway API is
`internal/protocol/schema/home_gateway.tsp`, and `scripts/check-home-gateway-compat`
refuses a Home Gateway change that is not an addition. The phone's Noise framing is
pinned by `internal/cloudlink/testdata/noise_vectors.json`, and the Cloud Relay frames
and signatures of both clients by `internal/cloudlink/testdata/cloud_relay_vectors.json`.

## Sub-features

- `phone-access-setting`: the experimental switch. While it is off, the daemon holds no connection to Attn Cloud, and the Home Gateway refuses every hello. Turning it off closes the link and ends every phone's conversation.
- `cloud-link`: while phone access is on, the home registers once, again if its Cloud Relay was deleted, keeps one socket to its Cloud Relay with a ping every 15 s, and reconnects after a loss from 100 ms backing off to 10 s. Settings → Phones shows connected, connecting, or the last error, such as the Cloud Relay's limit on new relays in a day.
- `pairing`: Settings → Phones shows a QR code per profile. Its secret works once, for 10 minutes. The Cloud Relay admits an unknown phone only with the relay token derived from a live code's secret, sent in the phone's `auth` frame while it pairs, and the home hears nothing of any other phone. The first message the phone sends after the handshake writes the pairing.
- `pairing-window`: a code's window ends when it is used, in the same allowlist frame that adds the phone, when the person clicks Cancel or leaves Settings → Phones, when the app that showed it quits or loses its daemon connection, when a new code replaces it, when its profile is deleted, and when it expires. Each sends the Cloud Relay a new allowlist, so a socket from the lapsed window closes with `4403`. Each profile's window closes alone, and a client that goes away ends only the codes it still holds, never a code another client replaced it with or a pairing already made.
- `revoke`: removes the pairing, sends the Cloud Relay the new allowlist, and closes the phone's conversation with that profile.
- `home-gateway-hello`: the phone says hello with its api version. The home answers welcome, serving min(the phone's api, `HOME_GATEWAY_API_VERSION`), with the home's name and the pairing's profile, or refused with a reason.
- `home-gateway-sessions`: after welcome, and again whenever one changes, every session of the pairing's profile, with its state mapped to the Home Gateway's states and its main terminal. Sessions of other profiles never reach the phone.
- `phone-crew`: from api 8, a session of a crew member carries `crew_member`, `crew_member_name` and `chief`, and the `sessions` event's `asleep_crew` lists the profile's members with no session. The Queue tab's Crew section comes first, above Asks, with the Chief first and then the desktop's order by member key. A member keeps its row whatever its state and is not listed again under Waiting, Working or Offline, and a waiting member still counts in the waiting badge. A member on an unreachable outpost or home shows offline in its row. A home older than api 8 sends no crew data, so the phone shows no Crew section.
- `phone-crew-wake`: tapping an asleep row sends `crew_wake`, which goes through the same wake as `attn crew wake`. The row shows waking until the home answers, and then it opens like any session row once the member's session arrives. A member that is awake or waking gets no second session. A refused wake shows the home's reason on the row and can be tapped again, and so can a member whose session ended before the home listed it. A wake from a phone below api 8 is not served. Phones have no way to put a member to sleep; a member sleeps through its own handoff.
- `phone-terminal`: tapping a live session on the phone opens its terminal, fitted to the phone's width with rows for the screen with the keyboard closed. The phone asks for that size and becomes the size owner (`size-owner` in terminals.md); the desktop then shows the terminal scaled until someone uses it there. The home answers `terminal_screen` (the visible screen as ANSI), then output frames, coalesced every 16 ms and sent only while the phone's credit allows. A phone that falls more than 1 MiB behind gets a fresh screen instead of the backlog. The terminal attaches again after every reconnect, including when the app returns to the foreground on a new connection. A phone that reconnects while the home is starting is welcomed only after the home has its terminals back. Opening the keyboard pans the terminal so its bottom rows, where the agent asks and the cursor waits, stay above the keys bar; it never resizes the PTY. Dragging the terminal down first pans the rows the keyboard hides, then scrolls back. A program that scrolls itself, such as Claude Code's fullscreen interface, gets mouse wheel reports as the desktop's wheel sends them; otherwise the phone scrolls through the output it has received since its latest `terminal_screen`, which each attach and each fresh screen starts over. A double tap returns to the latest output; a program that still tracks the mouse gets as many wheel-down reports as the phone sent it net wheel-up.
- `phone-keys-bar`: one row under the terminal: Esc, ↑, ↓, ⏎, 1, 2, 3, Tab, ^C, ⇧Tab, led by Hide while the keyboard is open, which closes it in one tap. A tap on the terminal closes it too; a drag scrolls instead. A key sends its bytes as the person's keystrokes and keeps the keyboard open. While the home is not connected, the session screen says so and the keys are off.
- `home-gateway-garden`: from api 6, after welcome and on every garden change, the open seeds of the pairing's profile without their bodies, packed into `garden_seeds` frames that fit one Cloud Relay frame, then `garden` with every open seed's id. `seed_get` answers a seed's body, checks, children and the newest log entries that fit a frame. From api 7 the home sends `seed_changed` with a seed's id whenever a `garden.seed.*` fact names a seed of the pairing's profile, so a change that leaves the seed's summary as it was, such as a note or a body edit, still reaches the phone. `seed_note` and `seed_move` (park, harvest, wither, replant, with text) act as the user through the desktop's note and transition paths, moving a seed an agent tends as the board does. A seed of another profile reads as absent.
- `phone-garden`: the Garden tab lists plots with their progress, then seeds growing, ready, blocked and parked. A pairing that is not online, or has not sent its garden yet, gets a line at the top naming it; its last seeds stay listed, greyed and labelled with the connection state, and the tab says "Nothing is planted." only once every pairing that serves a garden has sent one and none lists a seed. A seed's screen shows its status and tender, the move buttons its state allows, its children, its markdown body (mermaid renders; images say they open on the computer), checks, a note box and the log. A move opens a form with a required reason. After a note or a move, whenever the home sends a changed copy of the open seed or `seed_changed` for it, and on every welcome from its home, the phone reads the open seed again.
- `phone-push`: a sealed notification through the Cloud Relay when an agent's stop opens a turn in the waiting state, when it needs an approval, and when an ask opens. A waiting stop that a notification started sends nothing in any flow. Such a stop pushes, also when idle, for a turn the agent opened with `attn turn open`, once per turn. A stop whose run failed pushes in any flow as `run_failed`, with no text, and the phone shows "run failed". While the link is down, a push waits for the next connect. A push older than 2 minutes is dropped, with the reason in the daemon log, and one wait pushes once per daemon run.
- `phone-composer`: a text field with autocorrect and dictation. Send asks the home to `submit_prompt`: the session monitor pastes the text and presses Enter when the agent is at a turn boundary. Each session keeps its own draft. The text stays until the home says it was delivered; a refusal shows the home's reason. While the home is not connected, Send is off.

## How to get to it

### People

- **Settings → Experimental** and the top of **Settings → Phones**, "Phone access" (`app/src/components/SettingsModalSections.tsx`), the home setting `phone_access_enabled`.
- **Settings → Phones** (`app/src/components/PhonesSettings.tsx`), listed under Connectivity, dimmed and marked off until phone access is on: the link, "Pair a phone" per profile with Cancel beside a shown code, the paired phones with Revoke.
- Their own shell: `attn settings set phone_access_enabled true`.

### Agents

- None. Phones are paired and revoked by the person.

## Driving it

Preconditions:

- A Cloud Relay of your own that passes the contract. Add `export ATTN_CLOUD_URL=http://127.0.0.1:<port>` to `$DRIVE_ENV` before starting the daemon. Without `ATTN_CLOUD_URL` the daemon dials `https://cloud.attn.codes`.
- Use the baseline instance with its app, or the daemon alone for the link and the protocol.
- For the phone app in a browser at a phone's size, run `pnpm --dir mobile exec vite --port 5180` with a Vite config that resolves `./appleCrypto` to `src/test/nobleCrypto.ts`, because the app encrypts only with CryptoKit and a browser has no CryptoKit. Pair it by pasting the QR code's text in Pairings. The client that asked for the code must stay connected while the phone pairs, because the code's window ends when that client leaves, so `wsctl request` is not enough. The Cloud Relay stand-in checks a phone's `Origin`, so serve the page and the relay from one host and port. A browser reports no keyboard, so check keyboard behavior on an iPhone.
- Make a proof folder with `P=$(mktemp -d /tmp/drive-attn-phones-proof.XXXX) && echo "export P=$P" >> $DRIVE_ENV`.

- **Off by default.** `./attn settings get phone_access_enabled` prints an empty line, which reads as off, and `ss -tnp` shows no connection from the daemon's pid to the Cloud Relay.
- **The person turns it on.** Press ⌘, (`bridge native_key '{"key":",","modifiers":["command"]}'`), click `[data-testid="settings-nav-experimental"]` natively, and click `[aria-label="Phone access"]` natively after `dom_native_point` scrolls it into view. `./attn settings get phone_access_enabled` prints `true`, and the daemon holds one connection to the Cloud Relay. From the person's shell, `./attn settings set phone_access_enabled true` does the same.
- **Pairing and revoke.** Click `[data-testid="settings-nav-phones"]` natively, then "Pair a phone" in the profile's section. Click Cancel beside the code to end it, or leave the page, which does the same. To prove the relay token with a real phone, revoke it first, because the Cloud Relay does not check the token of a phone on the allowlist. A phone is the test phone in `internal/testworld/phone.go`. The stack test drives it end to end: `./scripts/test-go.sh --packages -v -run 'Phone|Pairing|TestEachProfile|TestDeletingAProfile|TestOnlyTheHome|TestUnreadableCloudKeys' ./cmd/attn`, against a Go stand-in for the Cloud Relay, or against a real Cloud Relay with `ATTN_TEST_CLOUD_URL=http://127.0.0.1:<port>`.
- **The Home Gateway.** `./scripts/test-go.sh --packages -v -run 'TestHomeGateway|TestAPhone|TestAHome' ./internal/daemon`.
- **The Crew section.** Set `crew_v2_enabled`, run `./attn crew create Keel`, then wake one member and leave another asleep. In the phone app, Queue lists Crew first with the Chief on top. Tap the asleep row: it shows waking, then `./attn crew list` shows the member awake, and the row opens its session.
- **The phone terminal.** Spawn a Claude Code session in the paired profile and tap it in the phone app. The terminal shows the agent at the phone's width, and `attn debug daemon-log --grep pty_resize` shows a resize to the phone's size. Answer a numbered menu with the keys bar, and send a prompt from the composer. After a long reply, swipe down on the terminal and read text from well above the screen; a double tap returns to the bottom. In the desktop app, the tile shows the terminal scaled; clicking it takes the size back.
- **The phone Garden.** Plant a plot in the paired profile with `./attn seed plot -f <file> --profile <id>`, a markdown body with a mermaid block and two children where one waits for the other. In the phone app, open Garden: the plot lists with its progress. Open the plot, then a child; add a note and park the child with a reason. `./attn seed notes <child>` shows the note by the user and the park's comment, and `./attn seed show <child>` shows it parked.
- **Proof.** In `$P`, keep each `./attn settings` command's output, the `ss` lines, the test output, and `bridge capture_native_window_screenshot '{"path":"<P>/phones.png"}'` of Settings → Phones, `<P>` written out.

## Contexts

- **Profiles**: a pairing reaches only its profile. The profile comes from the pairing, never from the phone's hello. A phone pairs with each profile separately, with one QR code each. Deleting a profile removes its pairings and disconnects its phones.
- **Outposts**: an outpost's sessions reach the phone through the home, with `host` set, and `offline` while the outpost is unreachable. A phone terminal of an outpost session survives the outpost going away: the phone says the terminal is lost until the outpost answers again, and then gets a fresh screen without reopening it. Only the home connects to Attn Cloud: an outpost that copies phone access from its home holds no link, and its Settings → Phones says why.
- **Restarts**: the home's keys and pairings survive a restart. A live QR code does not; show a new one. Keys attn cannot read stay in place; Settings → Phones names the file and how to start over.
- **Desktop reconnects**: Settings → Phones reads the phones again on every new daemon connection. A code shown before the connection dropped has ended, so the person shows a new one.
- **Cloud Relay deploys and network loss**: the Cloud Relay drops busy sockets without a close frame. The home reconnects, a waiting push goes out, and every phone runs a new handshake.
- **A deleted Cloud Relay**: a Cloud Relay with no home for 180 days deletes itself and its push tokens. The home registers again by itself. A phone registers its token again the next time it connects to the home, so until the person opens the app with the home online, the phone's pushes fail, and only the daemon log shows it.
- **Version skew**: a phone from before relay tokens that scans a code gets `4403` from the Cloud Relay and shows its old "no longer allows this phone" line, because it does not read the close reason; a phone already paired keeps working. A phone decodes a session state it does not know as `unknown` and skips an event it does not know. A home older than Home Gateway api 4 cannot open terminals; the phone says so instead of showing one. From api 5 a phone asks for an ask's HTML image by its source with every character reference decoded once, and the home reads exactly that image. A home before api 6 sends no garden; the phone's Garden tab names it as too old. A phone before api 6 gets no garden frames. A phone before api 7 gets no `seed_changed`; it still rereads the open seed on welcome. A phone before api 5 leaves named references other than `&amp;`, `&lt;`, `&gt;`, `&quot;` and `&apos;` undecoded; the home reads the decoded source when only that one is an image of the ask, and answers with an error naming both images when the source and its decoding each are.
- **Several clients on one terminal**: the phone, the desktop and other phones each ask for their size; the last one the person used owns it, as `size-owner` in terminals.md describes. A phone that disconnects or closes the terminal hands the size on.
- **Performance and idle cost**: with phone access off, nothing runs. With it on and no phone connected, the home sends one ping every 15 s. An open phone terminal that is quiet runs no timer on the home.
