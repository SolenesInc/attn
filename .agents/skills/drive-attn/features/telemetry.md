# Telemetry

What attn records about its own use, kept in an outbox and uploaded only when
the user turns it on. With usage analytics on, attn writes redacted records of
its event bus, app actions, `attn` command outcomes, agent runs and resource samples to an
outbox on each machine, and an outpost forwards its outbox to the home. It keeps the records 7 days, or 30 days for records not
yet sent while sharing is on. **Settings → Analytics** shows every
record the home holds exactly as it is stored, and names each outpost it can't reach. Sharing uploads the outbox to attn's
maintainers. Usage analytics and sharing are both off by default.
`docs/guide/reference/telemetry.md` says what each record holds and what leaves
the machine. Vents live in the same section. See
[vents.md](vents.md) for them.

## Sub-features

- `recording`: `analytics.enabled` turns recording on for the home and its outposts. It is experimental and off by default.
- `streams`: `bus`, `app`, `cli`, `sample` and `run` records, redacted before they are stored, and `vent` records the user sends.
- `outbox`: the records kept 7 days (30 days for unsent records while sharing is on), listed newest first by stream in **Settings → Analytics**, exactly as stored.
- `sharing`: an upload every 5 minutes, and once when sharing turns on. A refusal shows with its limit.
- `forget-install`: delete what the server holds and start a new install.
- `clear-record`: delete the local outbox and dismissed vents.
- `ingest`: attn-ingest, the service that receives uploads (`cmd/attn-ingest`, `docs/internal/attn-ingest.md`).

## How to get to it

### People

- **Settings → Experimental**, the "Usage analytics" switch, `settings.feature.analytics.enabled` (`native/crates/attn-app/src/settings/pages.rs`). **Settings → Analytics**, `settings.nav.analytics`, has the same switch in its page head. Opening the settings dialog is in [settings.md](settings.md).
- **Settings → Analytics** (`native/crates/attn-app/src/settings/analytics/view.rs`): the "Usage analytics" switch in the page head, with the page dimmed while it is off, then the strip (Sharing, Vents, Kept here, and Outposts when there are any, naming the unreachable ones), the lists Vents, All records, `bus`, `app`, `cli`, `sample` and `run`, and the inspector, which shows a record's JSON under "Exactly as stored". Keys: `[` and `]` switch lists, `j` and `k` or the arrows move, Enter expands a burst of records from the same second, `c` copies a record's JSON, `r` refreshes, `m` opens Machine settings.
- Machine settings, `settings.analytics.machine`: "Share with attn's maintainers" (Enable or Disable, then "Delete from server" after sharing ran), "Send vents", "Tool vents", Forget this install and Clear the local record.
- Their own shell: `attn settings set analytics.enabled|analytics.sharing_enabled|analytics.share_vents|analytics.tool_vents true|false` and `attn settings get` (`cli/attn/src/commands/settings.rs`).

### Agents

None. Agents do not read or change telemetry. attn records their `attn` commands (Triggers). See [vents.md](vents.md) for their vents.

### Triggers

- While recording, the daemon mirrors every event bus fact except `vent.*` into the outbox (`internal/daemon/analytics_mirror.go`). The daemon also records app actions (`internal/daemon/analytics_records.go`). Each `attn` command sends one `cli` record as the command exits (`cmd/attnd/analytics.go`). The record is named by the command path, and the daemon adds who ran the command. Socket requests write no record. Every 20 minutes the daemon takes a resource sample: memory by process role (itself, its PTY processes, each connected app and, for the Tauri app, its WebKit processes, found from the `app_pid` in the app's `client_hello`) and its workload (`internal/daemon/analytics_samples.go`, `internal/diag/process_memory*.go`, `internal/diag/webcontent_split_darwin.go`). For a connected native app it also sends `app_performance_request`, and the app's link thread answers with its CPU time and main-window frames since the last answer (`native/crates/attn-client/src/performance.rs`), which the sample keeps as the `app` entry's `performance`. The link measures only while `analytics.enabled`, as `initial_state` and `settings_updated` give it, is on, so turning recording on starts a fresh measurement, and losing the connection drops what was measured until the next `initial_state` says whether to record (`native/crates/attn-client/src/link.rs`). At each start with recording on, it records one `daemon_start` record that says how the previous run ended (`internal/daemon/daemon_run.go`). `attn daemon stop` and a replacing `attn daemon ensure` leave the stop note it reads, `<data-dir>/daemon-stop.json` (`internal/daemonctl/stop_note.go`), and the daemon keeps its own run in `<data-dir>/daemon-run.json`. When an agent's run ends, the daemon writes one `run` record after its next transcript read (`internal/sessionmonitor/runs.go`, `internal/daemon/analytics_runs.go`).
- While sharing, the daemon uploads every 5 minutes and once when sharing turns on (`internal/daemon/analytics_ship.go`). It uploads to the URL in `ATTN_ANALYTICS_INGEST_URL` from the daemon's environment. Without that variable, the default instance on the default data folder uploads to `https://attn-telemetry.caketroll.cloud`, and every other instance to `http://127.0.0.1:1`, where nothing listens (`config.AnalyticsIngestURL`). The Share row in Machine settings says where uploads go, and why an instance other than production uploads nowhere. `wsctl request --json '{"cmd":"get_analytics_status","request_id":"s"}' --event get_analytics_status_result` prints the same from the daemon (`ingest_url`, `ingest_off_reason`), with the last refusal.
- Records older than 7 days leave the outbox. While sharing is on, records not yet sent wait up to 30 days.

## Driving it

Preconditions:

- Use the baseline instance with its app, launched as [../SKILL.md](../SKILL.md) says, then `bridge wait '{"target":{"key":"home"}}'`. On Linux, run every command that reaches the app inside one `xvfb-run -a -s '-noreset -screen 0 1600x1000x24' bash -c '…'`, and press `mod+shift+,` where the steps press `mod+,`.
- Make a proof folder with `P=$(mktemp -d /tmp/drive-attn-telemetry.XXXX) && echo "export P=$P" >> $DRIVE_ENV`.
- For the sharing steps only, start a local attn-ingest on `127.0.0.1:8080`, as the "Running locally" section of `docs/internal/attn-ingest.md` describes. `make ingest-clickhouse` needs Docker, and `go run ./cmd/attn-ingest` needs `ATTN_INGEST_CLICKHOUSE_URL`, `ATTN_INGEST_IP_SECRET` and `ATTN_INGEST_LISTEN=127.0.0.1:8080`. Then append `export ATTN_ANALYTICS_INGEST_URL=http://127.0.0.1:8080` to the env file and start the daemon again in the instance shell. If you cannot do both, skip the sharing step and report it skipped.

- **Turn recording on in the app.** Press `mod+,` (`ui.openSettings`) and `settings.nav.experimental`. `settings.nav-off.analytics` reads "off". Press `settings.feature.analytics.enabled`, the switch named "Usage analytics": `bridge wait '{"target":{"key":"settings.nav-off.analytics"},"gone":true}'` answers and `./attn settings get analytics.enabled` prints `true`.
- **Off and on from the shell.** Run `./attn settings set analytics.enabled false`. It prints `analytics.enabled = false`, and `bridge wait '{"target":{"key":"settings.nav-off.analytics"}}'` answers. Run `./attn settings set analytics.enabled true` to turn it back on: `settings.nav-off.analytics` goes.
- **Read the outbox.** Press `settings.nav.analytics`. `bridge state '{"of":"settings"}'` shows `activeSection: "analytics"`, and `settings.analytics`, the page, has the keyboard. `settings.analytics.stat.sharing` reads `Off`. Press `]`: the tab `settings.analytics.views.all` is selected and `settings.analytics.list` lists `list-box-option` rows named `<time> · <name> · <stream>`. Press `j`: `settings.analytics.record.raw` holds the record's JSON under "Exactly as stored". Where the record has them, attn replaces free text with its length, such as `{"s":24}`, and subjects and ids with `h:` and 12 hex digits. A `setting.changed` record names its setting instead, such as `"subject":"analytics.enabled"`.
- **A burst.** Press `settings.analytics.views.bus`, run three `./attn settings set analytics.tool_vents true|false` in the background of one command so they land in the same second, and press `r`: the first row reads `setting.changed ×3 · bus`, and `settings.analytics.record.heading` reads `3 records in the same second`. Press `Enter`: the burst's records are separate rows.
- **Ids join to subjects.** Run `wsctl add-session --cwd $P --agent claude --label keyed-agent --id keyed-agent`, then `./attn seed plant "Keyed id drive" --session keyed-agent`. `wsctl request --json '{"cmd":"list_analytics_records","request_id":"r1","limit":500,"stream":"bus"}' --event list_analytics_records_result` lists `garden.seed.planted` with a `caused_by_session_id` equal to the `subject` of the `session.*` records. Run `./attn settings set new_session_destination_local_/home/someone/shop main_repo`: the newest `setting.changed` record has `"subject":"new_session_destination_<repository>"`, with no path.
- **A command outcome reaches the `cli` list.** From the shell, `./attn doc nope` exits 2 with `doc: unknown command "nope"`. In the app, press `settings.analytics.views.cli` and `r`: a row reads `doc · cli`. For refusals, run `./attn seed show s-zzzzzz` (exits 1), then `wsctl request --json '{"cmd":"list_analytics_records","request_id":"r1","limit":5,"stream":"cli"}' --event list_analytics_records_result`: the newest record is `seed show` with `"error_kind":"refused"` and `"refusal":"not_found"`, and no `query` record sits beside it.
- **A run reaches the `run` list.** A run needs a live agent, so spawn a Claude session in the app, type one prompt and wait for its stop. Press `settings.analytics.views.run`, then `r`: the list shows a `run` record whose JSON reads `"started_by":"user"`, an `ended` state and `"usage":"known"` with `tokens`.
- **App actions.** Press `settings.nav.experimental`, `settings.nav.analytics` and `settings.analytics.views.app`, then `r`: the list shows a `settings_section` row for each section opened, and the newest record's JSON reads `"props":{"section":"analytics"}`. The app records shortcuts and palette commands, Settings sections opened and queue advances.
- **Performance in samples.** The daemon takes a resource sample at most 20 minutes after recording starts. Press `settings.analytics.views.sample` and `r` until the list shows a `process` record, with a 21-minute deadline. Its `app` entry has `"shell":"native"` and `performance` with `period_ms`, `cpu_ms`, `frames_drawn`, `frames_unchanged`, `frames_skipped` and, once the window drew, `frame_ms` with `p50`, `p95`, `p99` and `max`. Leave the app idle until the next sample: its `frames_drawn` is 0 and its `cpu_ms` stays near 0. Turn recording off, use the app for a few minutes, then turn it on: the next sample's `period_ms` counts only from turning it on. Restart the daemon with `attn daemon stop` and let the app start it again: the next sample's `period_ms` counts only from the reconnect.
- **Daemon runs.** With recording on, run `./attn daemon stop`. The app starts the daemon again on its own. `wsctl request --json '{"cmd":"list_analytics_records","request_id":"r1","limit":5,"stream":"sample"}' --event list_analytics_records_result` lists a `daemon_start` record with `"previous_end":"stopped"`, `"stop_reason":"stop"` and a `previous_run` equal to the subject of the previous run's `process` samples. A daemon killed with SIGKILL gives `exited_unexpectedly` at the next start, and `attn daemon ensure` from a different build gives `stopped` with `source_fingerprint_mismatch`. After a failed `attn daemon ensure` the app says why in its Reconnecting banner and tries again, so it never stops a daemon with `app_recovery`.
- **Machine settings and clearing.** Press `m`: `settings.analytics.machine` shows the share row, whose `settings.analytics.machine.share.copy` says where uploads go, `settings.analytics.switch.analytics.tool_vents`, "Kept for 7 days", Forget and Clear. Run `./attn settings set analytics.share_vents true`: `bridge wait '{"target":{"key":"settings.analytics.machine.send-vents"}}'` answers with sharing still off, and it goes when the setting goes back to `false`. Press `settings.analytics.switch.analytics.tool_vents` twice: `./attn settings get analytics.tool_vents` follows it, `true` and then `false`. Press `settings.analytics.clear`, then `settings.analytics.confirm.yes`: `settings.analytics.toast` reads "Cleared", described "Cleared <n> records and <n> dismissed vents.". Recording stays on for the next step.
- **Share with a local attn-ingest.** Only with the sharing preconditions. Sharing uploads only while recording is on, and the clear above emptied the outbox, so first run `./attn doc nope` to record a command outcome. Run `./attn settings set analytics.sharing_enabled true`: it prints `analytics.sharing_enabled = true`, and an upload starts at once. Press `settings.analytics.views.all` and `r`: `settings.analytics.stat.sharing` reads `On ·` and when it last sent. `curl -s 'http://attn:attn@127.0.0.1:18123/?database=default' --data-binary "SELECT count() FROM events WHERE install_id = '$(jq -r .install_id "$(./attn instance resolve --field dataDir)/analytics-token")'"` prints a number above 0. `./attn settings set analytics.sharing_enabled false` stops the uploads.
- **Stop recording from the app.** Press `settings.feature.analytics.enabled`, now in the page head: `./attn settings get analytics.enabled` prints `false`, `activeSection` stays `analytics` and `settings.nav-off.analytics` shows.
- **Proof.** In `$P`, keep each `./attn` command with its output and exit code, `bridge tree` after each step on the page, and `bridge shot '{"path":"<P>/analytics-records.png"}'` with a record open, where `<P>` is the folder's path written out. With sharing, keep the `curl` reply. Name each file for its way in, such as `telemetry-shell-toggle.txt`. The `native-analytics-settings` scenario runs the page's steps.

## Contexts

- **Durability across restarts**: each daemon start classifies how the previous run ended from the run file, the stop note and the machine's boot time, so restarts, crashes, upgrades and reboots read apart on the server. The outbox, the install token (`<data-dir>/analytics-token`) and the subject secret (`<data-dir>/analytics-secret`) live in the data folder and survive restarts. A fact delivered again after a crash is stored once.
- **Linux**: the daemon records and uploads the same where it runs on Linux. **Settings → Analytics** is in the app, and `ui.openSettings` is Ctrl+Shift+, there.
- **Outposts**: `analytics.enabled` and the other analytics settings are home settings. Each outpost records to its own outbox with the home's subject secret, and forwards it to the home every 5 minutes under a stream that names the outpost, such as `bus_m9c1e04b7aa21`. Only the home uploads. Turning analytics off, Clear and Forget end what an outpost holds: the home refuses its records at once, and it deletes them when it next hears from the home. An outpost that can't reach the home keeps recording locally until then. An outpost samples the same way, without the `app` and `webkit_*` roles, since it has no app, and `panes_drawn` stays 0.
- **Profiles**: records are the daemon's, across every profile. A vent record is listed only in the profile its vent belongs to.
- **Performance and idle cost**: one resource sample every 20 minutes, and an upload carries at most 5,000 records. The open Analytics page does not animate or change while idle. Each sample's `app` entry carries the app's CPU time and frames drawn since the last one. The outbox mirror is an event bus consumer, so a stalled mirror pins the log. `attn bus status` shows the mirror ([diagnostics.md](diagnostics.md)).
- **Harnesses**: each `cli` record carries the harness of the agent that ran the command, and session facts and `run` records carry the harness, the reported model and the requested model. A harness with no watched transcript writes `run` records with `"usage":"unavailable"`.
- **Keyboard and native input**: every list action is one key, listed at the foot of the page, and the section takes focus when it opens. Keys typed into a text field do nothing to the lists.
- **Compatibility across versions**: attn-ingest accepts event names and streams it has never seen, so a newer build loses nothing to an older service. attn-ingest counts the records of a retried batch as duplicates and adds no rows.

## Gotchas

- An instance on a copy of production data keeps production's `analytics.sharing_enabled`. It still uploads nowhere, because the instance, not the data, picks the URL. Exporting `ATTN_ANALYTICS_INGEST_URL` to the real service in the instance shell would send it there.
- With `analytics.enabled` off the home and connected outposts record and send nothing, whatever the other settings say, and **Settings → Analytics** is dimmed and marked off with `settings.nav-off.analytics`.
- In the Tauri app (the rollback), a click that removes the focused control, such as a "Clear…" or "Forget…" confirm, or `m` pressed on a Machine settings button, leaves the page without focus. The page's keys do nothing until you click a row or button inside the page.
- The record lists load when a list opens. A record made while the list is open shows only after `r` or the Refresh button.
- Turning recording off and on again starts the mirror at the head of the bus: facts from the gap are never recorded.
- `c` copies a record's JSON to the clipboard, which on a shared Mac is the user's own. Leave `c` undriven there and report it blocked.
- `vent.*` facts never reach the outbox. A vent becomes a record only when it is sent.
