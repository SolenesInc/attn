# Markdown tiles

Open a markdown file in a tile, rendered and live as the file changes. An
agent shows the user a plan, a report or a design this way, beside itself. The
user opens files with ⌘P, from a terminal link or from their own shell. The
tile follows edits on disk, so a document the agent keeps writing stays
current while the user reads it. For review notes on a markdown tile, see
[annotations.md](annotations.md).

## Sub-features

- `file-open`: `attn open <file.md>` docks a markdown tile beside the caller, or beside the active tile when no session calls. A seed id opens a seed tile instead ([garden.md](garden.md)).
- `file-opener`: ⌘P lists recent files on an empty query, fuzzy-searches the active agent's folder, and browses folders for a query starting with `/`, `~`, `./` or `../`. A recent file's row ends with its latest touch, a pencil for an agent's edit or an arrow for an open, and how long ago. With outposts on, each row is tagged with its machine, ⇥ and ⇧⇥ list one machine's files at a time with its chip in the field, and ⌫ in the empty field lists every machine again.
- `recent-files`: files opened or edited before, best first. A file used often and lately ranks above one used long ago, and a file touched just now ranks first, with a lead that fades over the next couple of hours, so a file an agent just edited comes first. Picking one returns to the file's tile when that tile is still open.
- `markdown-render`: headings, tables, alerts, code with highlighting, images, Mermaid diagrams and frontmatter.
- `markdown-ids`: the ids of agents and seeds attn knows are links in documents, review documents' prose, seed bodies and notes ([garden.md](garden.md)), crew letters ([crew.md](crew.md)) and asks ([asks.md](asks.md)). Code, links and the Notebook's editor stay as they are. Markdown and terminals share the ids attn knows. [terminals.md](terminals.md) says how the app learns agent ids, and the **Performance and idle cost** context in [garden.md](garden.md) says how it gets seed ids.
- `live-reload`: the tile re-reads its file when the file changes.
- `terminal-link`: ⌘-click a markdown path in a terminal to dock it, bound to the session that terminal shows ([terminals.md](terminals.md)).
- `document-find`: ⌘F (`terminal.find`, Ctrl+Shift+F on Linux) on a plain markdown tile that holds the keyboard opens its find bar `tile.<m>.document.find`, whatever `vim_mode_enabled` says. Typing washes every match of the rendered text (`rune_kit::Markdown::find`) and centres the first; `tile.<m>.document.find.count` reads `<current>/<count>`. Enter and Shift+Enter step to the next and previous match, wrapping, and hand the keyboard back to the document; the bar's buttons step too, and Escape or its close button closes it and its washes.
- `vim-reading`: with `vim_mode_enabled` on (off by default; Settings → Appearance, the palette's `toggle-vim-mode`), the plain markdown tile holding the keyboard, with nothing focused, reads by vim keys (`native/crates/attn-app/src/vim.rs`, `markdown/keys.rs`): j and k scroll 24 points, Ctrl-d and Ctrl-u half the view, gg and G to the ends, ]] and [[ to the next and previous top-level heading, `/` opens the find bar and n and N step its matches. `g`, `[` and `]` wait 0.6 s for their second key, and Escape drops them. A terminal, a text field, a browser page and an open selection toolbar keep their keys. Switching to a desktop whose active tile is a document gives it the keyboard, so the keys work without a click. A `g`, `[` or `]` pending on one document never pairs with a key on another. The shortcuts sheet lists them while the setting is on. Seed tiles and the garden read by the same keys ([garden.md](garden.md) `garden-vim-reading`). A tile's find bar closes for good when its tile closes.
- `document-focus`: show the document alone on the desktop, and return with Escape.
- `open-in-editor`: open the active agent's folder in the user's editor.
- `review-document`: experimental, behind `code_review_enabled`. A markdown file with `attn: review` in its frontmatter is a review document. Its tile also receives a bundle: each `### path:from-to` stop resolved to rows of the file now with the change from base, its notes, flows and problems. The tile renders it in the frame its `frame:` picks (see `review-frames`). The Brief frame shows the title, then one line of facts (files, lines added and removed, and `N stops show X of Y changed lines`) whose Enter lists the changed files, then each stop as code rows with line numbers, the change from base and agent notes under their line, and the Not shown list. A keyboard cursor walks it.
- `review-frames`: a review document opens in the frame its `frame:` picks, and `1`, `2` and `3` switch, keeping the cursor's stop and line, also a line `e` widened into the stop when the target frame shows it. Walkthrough shows the document as a script beside the file view of the current stop, with the lines outside the stop dimmed. In every file view, the agent's notes on the cursor's line show in the strip under the file, above the user's marks on it. Map draws a mermaid `sequenceDiagram`, with the Not shown list under it, beside the document narrowed to the `##` step that holds the current message's stop, under a line naming the arrow; at tile width the diagram stacks above that step; with `mermaid before` and `mermaid after` fences, `b` switches between them, also to a side that ties no message to a stop. In the Brief, a drawn diagram replaces its fence as `.review-brief-diagram`: each arrow with a stop is a cursor place (`[data-review-cursor="message"]`) in document order, Enter on it opens the stop's file as Enter on the stop's row does, and with both fences only the current side's diagram shows, under the Before and After switch, which `b` flips; the Brief and the Map share that side. The Walkthrough's script shows the same diagrams with no cursor places, and `b` switches their side there too. A frame the document cannot fill is left out: Walkthrough needs a stop, Map a drawn diagram with a `%% stop:` message. The diagram is participants and actors (`<br/>` in a name starts a second line), messages, a `Note` after a message as its caption, a `Note` before the first message as the diagram's caption, and the blocks `rect`, `opt`, `loop`, `alt`/`else`, `critical`/`option`, `par`/`and` and `break` as boxes around their messages. A diagram with any other line stays a mermaid figure and is a problem in `attn review check`; so are a `Note` with no message before it in its block, a block with no `end` or no message, and an `end` with no block.
- `review-file-view`: from a review document, open any file whole with the change drawn in, the stop's range marked and the notes of every stop in that file on their lines, whichever way it was opened (a stop, the changed files, search, a navigation answer), go back through the files opened, and search the repository (files by name, lines by `git grep`), on the machine that holds the document.
- `review-marks`: on a review document, notes and questions on lines of a stop or the file view, and a send with a verdict. A note waits for the send. A question goes to the tile's session at once, stays in the draft, and the agent answers it with `attn review answer`; the answer shows under the line. The send lists the marks in reading order with their file, lines and quoted code, then the edits ([`review-edits`](#sub-features)), then the verdict, as one message. The send sheet lists everything the send carries, comments on the document's prose and overall notes included, and picks request changes when it carries anything and approve when it carries nothing. A send that a session awaiting approval skips keeps the draft, and the tile header reads Approval needed; the native app also keeps its sheet open saying why, with the verdict picked, until a send goes. A mark is anchored to its lines at the review's head and stays on them when the file changes; when any of those lines changed after head it shows under "Moved notes" at the end of the document and goes out labelled as moved. A delivered send records the head the user read, so the next `attn review start` takes it as the base.
- `code-navigation`: behind `code_review_enabled`. A shown review document starts a language server for each language its files are in, on the machine that holds the document, and the bundle's `navigation` lists each language's state (`starting` with the server's progress text and `started_at`, `ready`, `missing`, `failed`); the key line reads `go loading 12s: <progress>`, counting only while a server starts. `code_nav` answers definition, uses and type for a position, and the reader asks it with `gd`, `gr` and `K` on the line under the cursor. The asked line carries a `…` mark (`.review-row--asked`) until the answer, the error or Escape. An answer that takes over 1.5 s while the cursor moves, or arrives while search, an edit box or the composer is open, is an offer in the note line (`[aria-label="Offered answer"]`) once no box is open: Enter opens the definition or lists several places, Escape, another question or 20 s drop it, and every other key keeps its meaning. A question asked while the daemon is unreachable says so and to ask again. A definition outside the repository opens read-only. A server stops after `code_navigation_idle_stop_seconds` (300) with no review shown, including when an outpost loses its home's bridge, and a server a killed daemon left is reaped at the next start. A server that rejects `initialize` fails at once with its reason and leaves no process. Before each question the server is told which files changed on disk since it last asked, read from git: the folder's commit and dirty files, so edits, new files, commits and resets show in the next answer.
- `code-navigation-setup`: behind `code_review_enabled`. When a shown review has a language whose server is `missing` or `failed`, the key line offers `s set up` and `x not here` after that language's state; a failed state shows its reason. `s` sends `code_nav_setup` with the harness the user last picked (`new_session_agent`, while the catalog offers it; the offer reads `s set up with <harness>`), and with no such pick opens the harness menu beside the offer (`harness-menu.<harness>`: arrows, 1–9, Enter, Escape sends nothing), whose choice becomes the last pick and is sent. The home starts a delegation on the review's machine, in the review's repository, with that harness, whose seed holds the brief (`content/code-navigation/setup.md`). The agent shares the review's checkout with any agent already in it. The reply waits until the agent runs, so a launch failure shows in the key line's note with its reason. While that session is launching, working or waiting for approval the key line shows `<language> setting up in <session>`, a link that shows the session; once it stops with no working server, the key line offers `s set up` again and `s` starts another setup agent. A passing `attn nav check` turns the state `ready` in the open tile. `x` sets `code_review_setup_offer_<local|outpost-id>_<repository>` to `off`, which hides the offer for that repository; `s` still works and `x` again clears it.
- `review-document-stops`: a stop whose path ends in `.md` renders its range as a document, block by block. Changed blocks are marked; a light rewording marks its changed words, diffed over the rendered words; a block where more than half the words changed shows the old text struck above the new.
- `review-edits`: on a review document, `i` edits what the cursor is on and saves it to the file on the machine that holds it, against the hash the text was read with; a file that changed underneath is refused and nothing is written. The edit is listed under its lines, and `u` writes the newest edit's old text back. An edit stands between the lines at the review's head around it, found as marks are, and every view of its file reads it again after a save or an undo; when its text is no longer there, it shows under "Moved notes", where removing it drops it from the review without writing, and `u` does not reach it. The send numbers the edits on from the notes, each with the text before and after. A document stop on the home opens in an editor tile.
- `view-document`: experimental, behind `views_enabled`. A markdown file in the view language (an `<!-- attn-view 1 -->` first line, or a line outside code that opens one of the language's parts) opens as a view. The machine that holds the file checks it and reads its `file=` sources from the file's folder, and the tile draws each part natively in one reading column (`native/crates/attn-app/src/view/`), with the values in place. A part with a problem shows `Line <n>: <problem> <fix>` in its place while the others draw. With nothing focused, `j`/`k` and ↓/↑ move the highlight (the document's active descendant) over a list's head and rows, each question outside a one-by-one, each clip, and each one-by-one; Enter, ← and → fold a list's group; on a one-by-one, Enter keeps and `s` skips the current item, and ← and → step. See `view-answers` for questions. A `run=` source runs nothing when the view opens: a notice over the view names each command, how often it runs and the machine it runs on, and `r` or the notice's button sends `view_start`, which starts the commands the tile shows. The machine that holds the file then runs each command in the view's folder, without a shell, and reruns it at its `every=` while a window shows the view, skipping a tick while a run is in flight. A change to a command's line or to a file it names stops that command, fades the last values and says what changed until `r` starts it again; a failed run keeps the last values and shows why. A media part on a sound file (`.wav`, `.mp3`, `.m4a`, `.aac`, `.aif`, `.aiff`, `.flac`, `.ogg`, `.opus`) draws a player (`attn_ui::blocks::Audio`). The app reads the clip through `tile_asset_read` from the machine that holds the view, only while the clip is drawn on the current desktop (in a one-by-one, only the current item's), and forgets it once no view draws it there, so leaving the desktop stops it. A clip is read again when its view's text changes, and one that could not be read is read again when the view arrives again. Space plays or pauses the clip at the highlight, or else the view's first clip, and pauses any other; ⇧← and ⇧→ move it 5 s. While a clip plays the view repaints once a second, and never while paused. On Linux a clip shows its name and `audio does not play on Linux yet`, and the app reads nothing. `:::question-file`, `attn=` and `store=` sources, `:::entry` and `:::commands` say they are not available yet, and the controls of attn's commands are disabled. A view has no find bar, no annotation margin and no annotation controls in its header, the overview shows it as its card, and an `ago` value moves on at the minute.
- `view-answers`: experimental, behind `views_enabled`. The question parts take answers inside `::::each` and `::::one-by-one` too. On a highlighted question, or in a one-by-one's current item, digits pick a choice (again unpicks one of a `question-multi`), and `e` (Enter on a highlighted question) puts the keyboard in a `question-text`'s field, which keeps the text when Escape or a press leaves it; a text equal to its `Value:` is no answer. Keeping and skipping a one-by-one item are answers too, and its summary counts kept, changed (a rewritten `Value:`) and skipped. The app sends each answer at once with `view_answer`, and the home keeps it as a draft by the view's machine and path (`view_drafts`), so the answers outlive app and daemon restarts, and a one-by-one rests on its first item not kept or skipped. A tile an agent opened (`tile_session_id`) shows Send, also the send key (`markdown.sendAnnotations`, mod+Enter; mod+Shift+Enter on Linux): `view_send` writes `<view>.responses.json` beside the view on its machine and types `The user sent "<title>": <summary>. Responses: <path>` into that agent's conversation through its inbox, as an ask's answer goes (`internal/prompts/content/view/answers-sent.md`). The tile then reads "Sent. The agent has your answers in <path>.", or, when that agent's session is gone, that no agent was told. Drafts stay after a send, so Send again sends them all. A refused answer or send shows why under the view.

## How to get to it

### People

- ⌘P (`file.open`, `native/crates/attn-app/src/keymap.rs`) opens the opener (`native/crates/attn-app/src/opener/`). Inside a focused editor tile, ⌘P opens that tile's note finder instead ([notebook.md](notebook.md)).
- Palette (`native/crates/attn-app/src/palette/commands.rs`): `open-markdown-file` ("Open a markdown file"), and `open-in-editor` ("Open in editor"), offered while an agent is on screen, and `toggle-vim-mode` ("Turn on vim keys for documents" or "Turn off …").
- In a terminal, ⌘-click on a `.md` path, Ctrl-click on Linux (`native/crates/attn-app/src/terminal/links.rs`).
- Tile header (`native/crates/attn-app/src/desktop/view.rs`): "Focus document" `tile.<tile>.focus` (also ⌘⇧↩, `terminal.toggleMaximize`), which a focused document replaces with "Return to row" `tile.<tile>.return`, and "Close tile" `tile.<tile>.close`. The tile's row in the sidebar (`native/crates/attn-app/src/sidebar/mod.rs`) has a "Close <title>" button.
- In the document (`native/crates/attn-app/src/markdown/`): a fragment link scrolls the tile. Images open larger (`native/crates/attn-app/src/markdown/images.rs`). An id attn knows (`native/crates/attn-app/src/markdown/ids.rs`) is a link keyed `attn-session:<session>` or `attn-seed:<seed>`. Resting the pointer on it opens its card under it, `words.agent-card` or `words.seed-card`, and ⌘I (Ctrl+Shift+I on Linux) gives the card the keyboard. A click opens a live agent, gives a closed agent's card the keyboard, and opens a seed as a tile. Holding ⌘L (Ctrl+Shift+L on Linux) labels it, as in a terminal. From a popped-out tile, an agent or a seed opens in the main window.
- In a review document (`native/crates/attn-app/src/review/`), with focus in the tile, vim keys work whatever `vim_mode_enabled` says, each with its arrow or page key as an alias: j/k (↑/↓) by line in code and by block in prose, h/l, `[[`/`]]` (←/→) by stop, Ctrl-d/Ctrl-u half a page, gg/G (Home/End) to the first or last place, `V` starts a selection at the cursor that the moves extend (`V` again or Escape drops it), Enter opens the file at the cursor, `e` shows 10 more lines around the stop and its range label names the lines it shows, `z` fills the tile with the file, `/` searches (the empty box lists the changed files with their added and removed lines), ⌃o goes back, Escape closes the search, the key sheet or the file view, `?` shows the keys. ⇧↑/⇧↓ select several lines, `c` writes a note on them and `a` asks a question (Enter saves, ⇧Enter adds a line, Escape cancels); in the Walkthrough they work on the stop's file. `i` edits the selected lines, else a whole string or comment of several lines, else the line; in a document stop, the block as markdown. In the edit box ⌥↑/⌥↓ take in a line, Enter saves one line and ⌘Enter several (Ctrl+Enter on Linux, which the box names through `keyCombo`), Escape cancels. `u` on an edited line undoes the edit. In a document stop, `o` or the stop's "editor" button opens the file in an editor tile rooted at the repository, on the home only. ⌘Enter (Ctrl+Shift+Enter on Linux, which the key line and the key sheet name through the shortcut formatter) opens the send sheet: it lists the marks, then the edits, and takes the verdict with `a` (approve), `r` (request changes) or `c` (comment); Enter sends and Escape returns to the review. In the file view, j/k, Ctrl-d/Ctrl-u, gg/G and PageUp/PageDown move, h/l (←/→) go to the previous or next change, and H/L (⇧←/⇧→) scroll sideways by half the view's width. A long line wraps in a stop, under its text and past the line numbers; the file view keeps one row a line. A click on a row, a file in the changed files or a Not shown entry moves the cursor there or opens it; a stop's "file ↵" button opens its file. The key line at the bottom of the tile lists the frames and the keys for the current view, and wraps onto more rows rather than hide a key. `1`, `2` and `3` switch frames. In the Walkthrough, j/k move in the file, h/l go to the previous or next stop, H/L scroll the file sideways, `b` switches the script's diagrams between before and after, `z` hides the script, and ⌃o and Escape return to the stop's file. In the Brief, j/k also stop on each arrow with a stop in a drawn diagram, Enter there opens the stop's file, and `b` switches between before and after. In the Map, h/l go to the previous or next message with a stop and put its step's lead-in at the top, `b` switches between before and after, j/k move within the step, and the other keys work on it as in the Brief. On a line of code, in a stop or the file view, `gd` labels each name on the line and goes to the definition of the one whose label is typed (on a definition it lists the uses), `gr` lists the uses and `K` shows the type; a line with one name skips the labels. A list takes j/k, Ctrl-d/Ctrl-u, gg/G, their arrow and page aliases and Enter, and Escape closes it, cancels the labels or drops a question on its way. The key line shows each language's server state, with what a loading one is doing; a state too long for a row ends in an ellipsis, with its detail in the title. For a language with no working server, `s` starts an agent that sets one up, and `x` stops or restores the offer. Selecting text and typing still opens a comment ([annotations.md](annotations.md)).
- Settings: the editor command (`editor_executable`) that "Open in editor" runs. Without it, "Open in editor" runs `$EDITOR` or `$VISUAL`.
- Where people see what agents do: the tile an agent opens docks beside the agent's tile and follows the file as the agent writes it.
- Their own shell: `attn open <file.md> [--session <id>]`.
- The user guide: `attn guide code-review` (`docs/guide/reference/code-review.md`) covers turning the review on, the frames, the keys, marks, the send, and code navigation with its setup.

### Agents

- `attn open <file.md|seed-id> [--session <id>] [--profile <name|id>] [--json]`: a relative path resolves against the folder `attn` runs in. The tile docks beside the caller, or beside the tile of `--session`. The catalog defines it (`internal/catalog/content/open.yaml`), the CLI presents it (`cli/attn/src/commands/open/mod.rs`) and the command layer runs it (`runOpen`, `internal/daemon/tilecontent.go`). The app and the native app open documents and seeds with the `open_markdown` and `open_seed` wire commands.
- Tool, with `agent_tools_enabled` on: `open` over `/mcp`, with `path` (relative to the folder the session started in) or `seed`. A review document's problems (with `code_review_enabled`) and a view's (with `views_enabled`) come back as `problems`, and a view's `run=` commands with their state come back as `commands`.
- `attn review start <document> [--base <commit>] [--repository <dir>]` snapshots the working tree of the repository it runs in, or of `--repository`, as head and writes `frame`, `repository`, `base` and `head` into the frontmatter, creating the document when it is missing. `attn review check <document>` prints each problem with its line and the fix, and exits 1 when there are any. `attn open` on a review document prints the same problems as `attn open: warning:` lines and still opens the tile. `attn review answer --doc <document> <question-id> -m <answer>` stores the answer to a question the user asked; the question's message gives the agent this command. With `code_review_enabled` off, `attn review` refuses and names the setting. The catalog defines the three commands (`internal/catalog/content/review.yaml`); the CLI presents them (`cli/attn/src/commands/review/mod.rs`) and the command layer runs them (`internal/daemon/review.go`).
- Tools, with `agent_tools_enabled` on: `review_start`, `review_check` and `review_answer` over `/mcp`. A relative `document` or `repository` resolves against the folder the session started in, and `review_start` without `repository` takes that folder.
- `attn nav` (the catalog's `internal/catalog/content/nav.yaml`, presented by `cli/attn/src/commands/nav/mod.rs`, run by `internal/daemon/code_nav.go`, and offered to agents as the `nav_*` tools; `nav_check` as a tool answers `starting` after 20 s while the CLI waits): `status` lists the server for each language of the repository it runs in and the running servers with their memory, `check <path>:<line>` asks for the definition of each name on that line and passes on the first answer that is not the asked name itself, `link <program> [--as <name>]` and `unlink <name>` put a server binary in `<data-dir>/code-navigation/bin`, `set <language> <json>` and `rm <language>` write or remove the repository's definition in `code_navigation_<origin>_<language>`. With `code_review_enabled` off, each refuses and names the setting.
- Prompts: `attn skill --reference markdown` (`internal/prompts/content/skills/attn/references/markdown.md`), named in the attn map as "Show the user a markdown document" (`internal/prompts/content/session/attn-map/open.md`), and `attn open <plot>` in the seed craft (`internal/prompts/content/resources/seed-guide.md`).
- Prompts: `attn skill --reference review` (`internal/prompts/content/skills/attn/references/review.md`, generated from the catalog) teaches presenting a change: when to present, the base for `attn review start`, what a review contains, the frame to pick, answering a question and acting on each verdict. A session launched with `code_review_enabled` on finds two rows for it in its attn map (`internal/prompts/content/session/attn-map/review.md` and `nav.md`): "Present a change for the user to review", and "Set up code navigation in a review for a language with no working server". The question and the sent review arrive through the templates in `internal/prompts/content/annotations/` and repeat the commands.
- Prompts: `attn skill --reference code-navigation` (`internal/prompts/content/skills/attn/references/code-navigation.md`) says how to find, install, link and define a language server. It is the setup agent's guide, and the guide for anyone setting one up by hand.

### Triggers

- An open markdown tile re-reads its file when the file changes on disk, and shows an error when the file goes away or grows past 1 MiB (`internal/daemon/tilecontent.go`).
- An open review document also gets a new bundle when a file one of its stops shows changes (`internal/daemon/tile_documents.go`).
- The file view and search ask the daemon with `review_file` and `review_search` (`internal/daemon/review.go`). With `code_review_enabled` off, both refuse and name the setting.
- An edit sends `review_edit` with the file's path, the hash it was read with, the lines it replaces and the text; it runs on the document's machine and writes through `fsdoc.Store.Write` (`internal/review/file.go`). A changed file answers `conflict` and is left untouched; a file over 2 MiB is refused naming the limit. With `code_review_enabled` off it refuses and names the setting. The edit is an `edit` annotation with `edit_was` and `edit_now`.
- A question and a review go out through `markdown_annotations_submit`: `only_ids` asks the named questions at once, `verdict` and `head` send the review (`internal/daemon/ws_markdown_annotations_submit.go`). After a delivered review the daemon sends `review_sent` to the document's machine, which writes the sent ref. `review_answer` stores an answer and pushes `desktop_tile_content` with a new `annotations_generation`, and the tile re-reads the draft. With `code_review_enabled` off, `only_ids`, `verdict` and `review_answer` refuse and name the setting.
- `code_nav_setup` from the reader's `s` (`internal/daemon/code_nav_setup.go`) starts the setup delegation; the home records the setup's session per host, repository and language in its database and adds it to the bundle's navigation as `setup_session_id` when it sends the tile, so the link survives a home restart. With `code_review_enabled` off it refuses and names the setting.
- Showing a review document, and `attn review start`, start its language servers; a review leaving the watch set releases them and arms the idle stop (`internal/daemon/code_nav.go`, timer `code-nav-idle-stop`). A server whose state changes bumps the document's bundle. Daemon start reaps servers left in `<data-dir>/code-navigation/servers`.

## Driving it

Preconditions:

- Use the baseline instance with its app, launched as [../SKILL.md](../SKILL.md) says. Then run `bridge wait '{"target":{"key":"home"}}'`. On Linux, run every command that reaches the app inside one `xvfb-run -a -s '-noreset -screen 0 1600x1000x24' bash -c '…'`.
- Widen the window with `bridge set_window_bounds '{"logicalBounds":{"x":0,"y":0,"width":1900,"height":1050}}'`. At the default width a docked document is shelved as a tab at the top of the desktop.

## Contexts

- **Durability across restarts**: a markdown tile is part of its desktop and comes back after any restart, re-reading the file. Recent files are kept too. The file itself is the source, so a tile shows whatever is on disk now. A view's answers are kept at the home, so they come back as well.
- **Linux**: `attn open` works the same where the daemon and CLI run on Linux. The opener is Ctrl+Shift+P there (`native/crates/attn-app/src/keymap.rs`).
- **Outposts**: a markdown tile reads, watches and loads images and a view's sound clips from the machine that holds its file. `attn open` from an outpost agent, and a markdown file it sends, open the outpost's file, never a home file at the same path. Links to other markdown files open on that outpost; other local links name it. Drive it with `./scripts/test-go.sh --packages -run TestAMarkdownTileFromAnOutpostShowsTheOutpostsFile -v ./cmd/attnd`. A draft on an outpost tile is keyed by its host and path (document URI `attn://file/<path>?host=<id>`), apart from a home draft at the same path. Files an outpost agent sends or edits, also while the outpost is away, show in `recent_files` with `host` and in ⌘P tagged with the outpost (the row's accessible name ends `on <outpost>`), and open there. ⇥ lists one machine's files, and a typed `/` or `~` path then browses that machine. An unreachable outpost's rows are marked offline, and picking one notifies `Could not open <file>: <outpost> is offline` and opens nothing. Drive the opener's part with `cd native && cargo test -p attn-app --test wire opener`. `recent_files` lists each machine's own top `limit`. The outpost, never the home, checks whether its files still exist, and a file deleted there leaves the list, however many are deleted. For each request, the home gives an outpost one second in total to check its files. The files the outpost has not checked by then come back unchecked, and so do all the files of an unreachable outpost. On Linux, drive the outpost's files in `recent_files`, also those from while it was away, and a file deleted there with `./scripts/test-go.sh --packages -run TestAnOutpostsFilesKeepTheirMachineInRecentsAndDrafts -v ./cmd/attnd`. Drive the limit, many deleted files, the one-second wait, and a stalled and a lost outpost with `./scripts/test-go.sh --packages -run 'TestRecentFiles(KeepAnOutpostsOwnLimit|AnswerWithinASecond)' -v ./internal/daemon`. A review document on an outpost resolves, opens files and searches on the outpost; on Linux, drive it with `./scripts/test-go.sh --packages -run TestTheFileViewAndSearchOfAnOutpostsReviewReadTheOutpostsRepository -v ./cmd/attnd`. A question on it reaches the outpost agent, the agent's `attn review answer` lands in the outpost's draft, and a sent review writes the sent ref in the outpost's repository; on Linux, drive it with `./scripts/test-go.sh --packages -run TestAnOutpostAgentsReviewTakesItsAnswerAndRecordsItsSendOnTheOutpost -v ./cmd/attnd`. The editor tile is not offered for an outpost's document. A view on an outpost keeps its answers at the home and writes its responses file on the outpost. attn refuses ⌘-click on a path in a terminal on an outpost, and "Open in editor" for an agent on an outpost, with `<path> is on <outpost>; opening files on an outpost isn't supported yet`.
- **Profiles**: tiles open on a desktop of the caller's profile. Without a session, a tile opens on the current desktop of the profile used most recently.
- **Performance and idle cost**: each open markdown tile keeps checking its file while it is open, so tiles nobody reads still cost a little. Close them. attn refuses files over 1 MiB and names the size and the limit. A review reader colors each stop's file once after it opens, one file at a time, and keeps the colors of the files it has shown while their content is unchanged, up to 25,000 lines, so a file opened again is colored at once.
- **Harnesses**: every harness opens files with the same `attn open`.
- **Keyboard and native input**: ⌘P opens the opener from anywhere except a focused editor tile. In the opener, use the arrow keys, Enter and Escape; with outposts on, ⇥ and ⇧⇥ change the machine listed, and ⌫ in the empty field lists every machine. ⌘⇧↩ focuses the active document and Escape returns.

## Gotchas

- At the default window width a docked document is shelved as a tab at the top of the desktop. Widen the window first, as the preconditions do.
- `bridge press` aims at the middle of its target. On a view, the middle of `tile.<m>.document` can be a question's choice, and the press picks it. Press near the top with `"at":[0.5,0.04]`.
- `attn open` reads a bare name starting with `s-` as a seed id, so `attn open s-notes.md` is refused as `"s-notes.md" is not a seed id`. Pass `./s-notes.md`.
- Opening the same file twice returns to the file's tile instead of docking a copy. A recipe that counts tiles after a second open sees one. Opening the same file through `/tmp` and `/private/tmp` still creates two tiles, because path-alias reuse is not fixed yet. Keep the path spelling consistent when checking reuse.
- A path the agent resolves from a relative name comes from the folder it runs in. On macOS `/tmp` is `/private/tmp`, so compare file names, or resolve both sides with `realpath`.
- On an empty query the opener lists only files opened or edited before. A fresh instance shows none until a file is opened or an agent edits one.
- Without the app, `attn open` still places the tile in `tree_json`. Only the app renders it. Prove rendering with `bridge`, not the CLI.
- Working but wrong: a file that grows past 1 MiB, or is deleted, turns the open tile into an error, and the tile recovers on its own once the file is back under the limit. "Open in editor" opens the agent's folder, not the document in the active tile.
