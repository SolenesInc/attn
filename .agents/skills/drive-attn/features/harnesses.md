# Harnesses

Bring your own harness: attn wraps Claude Code and Codex as they are, Sigma
behind the experimental `sigma_enabled`, and plugins add more. Each agent runs its harness's own CLI with the user's
account, settings and conversations, and the user can run the bare CLI at any
time. People pick a harness for each agent, set each harness's executable and
default model, and install plugins. The sidebar can mark each agent with its
harness's logo.

## Sub-features

- `harness-choice`: pick the harness when starting an agent. The default comes from Settings.
- `harness-settings`: each harness's executable, default model and effort, and auto-approve, plus what it supports, in Settings.
- `harness-models`: the models each harness offers, and the light, standard and deep tiers mapped to them.
- `execution-targets`: where a plugin server's conversation runs its tools, from the targets the server lists for the folder, chosen at launch and kept through resume. An unavailable target ends the view with its reason and never falls back to local.
- `plugins`: install a plugin from a folder or a Git repository, link a folder while developing one, set a plugin's priority, uninstall.
- `plugin-driver`: a plugin's driver starts its harness's agents and reports what they do. A driver may declare a display name while keeping its stored harness ID. A run keeps its terminal or direct input route across disconnects and restarts. Capable drivers receive attributed input, accept text during approval without answering it, and compact before closing. A driver that declares `agent_tools` gets attn's MCP endpoint in `driver.spawn` and `driver.resume` while `agent_tools_enabled` is on.
- `plugin-server`: an installed plugin declares a shared app-server speaking `attn-app-server-v2` with the abilities it has (`watch`, `targets`, `compact`, `steer`, `question_safe`), prepares native views and exposes models and, with `targets`, execution targets. Open conversations retain direct input and ownership without a view. A server declaring `caller_conversation_header` is given attn's MCP server with `mcp/register` while `agent_tools_enabled` is on, and its views start conversations with the server's name.
- `plugin-authoring`: an author outside the checkout installs `@victorarias/attn-plugin`, copies `examples/plugins/sample-harness`, changes its harness ID and installs it with `attn plugin install --path`. The ID appears in the picker and launches the harness. A capability the author leaves out is unavailable.
- `sigma`: the built-in Sigma harness, offered while `sigma_enabled` is on and its executable is found. It runs on Sigma's shared server like `plugin-server`, with no plugin: the server link exists from daemon start, and the TUI runs `sigma --conversation <id>`, with `--auto` under YOLO, auto-approve (on by default) or in an automation run. Input reaches the server with an `{id, name}` author as a steer. It joins a working run. It never answers an approval: it waits in Sigma through an approval of the conversation's own run, and reaches the conversation at once when only a subagent waits. `attn agent close --self --compact` compacts through `conversation/compact` before the session closes. A Sigma server already running from a build that answers protocol 1 is refused, with a message that names its pid and the server attn starts once it stops. A delegation role's attn-workflow skill goes to the skill folders Sigma's `config.toml` names. While `agent_tools_enabled` is on, it gets attn's MCP server as `plugin-server` does: a new conversation starts with `--mcp-server attn=<description>` and the intent map after its instructions, and a tool call acts as the session that holds the call's root conversation.
- `harness-logos`: the Claude or Codex mark beside each agent in the sidebar, or a state dot without it.
- `shared-conversation-warning`: two tiles on one Claude Code conversation both warn until one closes.

## How to get to it

### People

- The new-agent picker's "Session agent" choice, ⌥1 to ⌥9 and ⌥T for a shell (`native/crates/attn-app/src/picker/view.rs`). See [agent-launch.md](agent-launch.md) for the picker itself.
- **Settings → Agents and models** (section `agents`, `native/crates/attn-app/src/settings/agents.rs`): the default session agent, each harness's executable, default model and effort, default context cap, "Auto-approve", "Direct agent launches", what each harness supports, model price overrides, and the "Seeds on standby" block: the choice of `garden.tender_resume` with its explainer of which mail resumes a closed agent ([garden.md](garden.md)), and the "Ring on my own PR comments" switch ([pull-requests.md](pull-requests.md)).
- **Settings → Models** (section `models`, `native/crates/attn-app/src/settings/models.rs`): the tiers mapped to each harness's models.
- **Settings → Plugins** (section `plugins`, `native/crates/attn-app/src/settings/plugins.rs`): the "Plugin source" field with Browse and "Install Plugin", a card per plugin with its version, a Linked mark for a linked plugin, its runtime state and health, a Remove button, and a priority field.
- Palette `toggle-harness-logos` ("Hide harness logos in the sidebar" or "Show harness logos in the sidebar", `native/crates/attn-app/src/palette/commands.rs`), the setting `sidebar_harness_logos_enabled`.
- Where people see what agents do: the sidebar row's logo, labelled "<Harness> · <state>" (`native/crates/attn-app/src/sidebar/mod.rs`), and the notice above a terminal whose conversation another terminal also runs, `session.<session>.shared-conversation` (`native/crates/attn-app/src/desktop/shared_conversation.rs`).
- Their own shell: the verbs below.

### Agents

- `attn plugin install --path <dir>`, `link --path <dir>`, `list`, `uninstall <name>` and `remove <name>` (`cmd/attnd/plugin.go`), each printing JSON.
- `attn settings get|set` for `new_session_agent`, `claude_executable`, `codex_executable`, `sigma_executable`, `sigma_enabled` and `sidebar_harness_logos_enabled` ([settings.md](settings.md)).
- Prompts: a plugin driver that asks for launch instructions gets the same agent or chief guidance as the other harnesses (`internal/harness/internal/plugin/plugin.go`). See [agent-guidance.md](agent-guidance.md) for what attn tells every harness.

### Triggers

- The plugin supervisor starts each installed plugin, restarts it when it fails, and stops it on uninstall (`internal/daemon/plugin_supervisor.go`). The plugin adapter launches its harness's agents (`internal/harness/internal/plugin/plugin.go`), and `internal/daemon/plugin_driver.go` handles driver registration and reports.
- attn asks each harness which models it offers (`internal/daemon/harness_models.go`).
- A protocol client lists a folder's targets with `harness_targets {harness, cwd}` and launches on one with `spawn_session`'s `execution_target` (`internal/daemon/harness_targets.go`). No app picker offers it yet.

## Driving it

Preconditions:

- Use the baseline instance with its app, launched as [../SKILL.md](../SKILL.md) says. Then run `bridge wait '{"target":{"key":"home"}}'`. Stay in desktop flow, the default. On Linux, run every command that reaches the app inside one `xvfb-run -a -s '-noreset -screen 0 1600x1000x24' bash -c '…'`.
- Make a proof folder with `P=$(mktemp -d /tmp/drive-attn-harnesses.XXXX) && echo "export P=$P" >> $DRIVE_ENV`. Make an empty agent folder `$P/codex`.

`<P>` is the proof folder's path written out.

- **The harnesses on offer.** Run `bridge key '{"chord":"mod+n"}'` and `bridge wait '{"target":{"key":"new-session"}}'`. The radio group "Session agent", `new-session.agents`, holds `new-session.agent.terminal`, `new-session.agent.claude` and `new-session.agent.codex`, with the keys ⌥T, ⌥1 and ⌥2. A plugin harness is listed once its plugin is installed and running. A harness the machine lacks has no key and is disabled, described as "<Harness> is not available on this machine". While the daemon checks which harnesses are installed, a harness stays selectable, described as "Checking for <Harness> on this machine", and carries the mark `new-session.agent.<harness>.checking`, named "checking". Settings marks its default agent buttons the same way. With an outpost as the target, Launcher 2.0 leaves off the description and the mark.
- **Pick with a key.** Run `bridge key '{"chord":"alt+2"}'`. `bridge tree` marks `new-session.agent.codex` checked, and `./attn settings get new_session_agent` prints `codex`: a pick is saved as the default. ⌥1 checks Claude and saves `claude`. ⌥T checks Terminal and leaves the saved default alone. Press Escape.
- **No pick yet.** On a fresh instance, before any pick, press Mod+N: no `new-session.agent.*` is checked. Type a folder and press Enter: nothing starts, the "Session agent" group wears the accent edge, and `new-session.agents.needed` beside it says "Choose a harness (⌥1–⌥9)" (Alt+1–Alt+9 on Linux). The empty desktop's launcher marks its toggle the same way, as `launcher.agents.needed`. A pick clears the mark. A pick that is later uninstalled leaves nothing checked the same way. `./attn` at a shell in a folder no agent works in opens this dialog with the folder typed in. With a pick, it starts the pick there. Press Escape.
- **The default from the shell.** Run `./attn settings set new_session_agent claude`. It prints `new_session_agent = claude`. Press Mod+N: `new-session.agent.claude` is checked. Press Escape.
- **The default agent in Settings.** Open Settings as [settings.md](settings.md) says and press `settings.nav.agents`. Press `settings.default-agent.codex`: `./attn settings get new_session_agent` prints `codex`. Press `settings.default-agent.claude` to put it back.
- **The switches.** Press `settings.toggle.auto_approve_enabled`, then `settings.toggle.direct_agent_launch_enabled`: `./attn settings get` follows each, and a second press saves the old value back.
- **A harness executable.** Press `settings.agent.codex.toggle`, then `settings.agent.codex.advanced`, so the Codex card and its advanced fields are open. Make an executable file, press `settings.setting.codex_executable`, type its path, written out, and press `Enter`: `settings.saved.codex_executable` answers and `./attn settings get codex_executable` prints the path. The daemon refuses a path with no executable file. Clear the field and press `Enter`: the setting is empty again and attn uses the `codex` on PATH.
- **A refused cap.** In `settings.setting.default_context_window_cap_codex`, type `1` and press `Enter`: `settings.refusal.default_context_window_cap_codex` reads `context window cap must be between` and the range. Press `settings.nav.general`: `state` of `settings` still shows `activeSection: "agents"`, because a refused field keeps its page. Type `192000` and press `Enter`: the refusal goes and the setting reads `192000`.
- **A price override.** Press `settings.pricing` to open the model price overrides. Type a model in `settings.price-new.model` and a rate in each of `settings.price-new.<rate>`, the five rates of `session_cost.price.<model>`, and press `Enter`: `settings.price.<model>` answers and `./attn settings get session_cost.price.<model>` prints the five rates. Press `settings.price.<model>.remove`: the row goes and the setting is empty. Press Escape to close Settings before the palette steps below.
- **Harness logos.** Run `wsctl add-session --cwd $P/codex --agent codex --label harness-codex --id harness-codex --place`. `bridge wait '{"target":{"key":"sidebar.session.harness-codex.state"}}'` answers, named `Codex · ` and the state. Open the palette with `bridge key '{"chord":"mod+shift+k"}'`, type `Hide harness logos` and press Enter. `./attn settings get sidebar_harness_logos_enabled` prints `false`, and the row shows its state dot where the logo was. Choose "Show harness logos in the sidebar" in the palette: the logos return.
- **A plugin from a folder.** Make a folder `$P/audit-probe` holding `attn-plugin.toml` (`name = "audit-probe"`, `version = "0.0.1"`, `attn_api_version = 7`, and `[plugin]` with `kind = "executable"` and `path = "probe.sh"`), a `package.json` of `{"name":"audit-probe","version":"0.0.1","private":true}` (install runs `bun install`, which needs one) and an executable `probe.sh` that runs `exec sleep 300`. `./attn plugin install --path $P/audit-probe` prints `"ok": true`, and `./attn plugin list` lists it. Run `./attn plugin uninstall audit-probe`. Then run `./attn plugin link --path $P/audit-probe` and `./attn plugin remove audit-probe` to do the same for a linked copy. The supervisor starts the probe and stops it on removal. Once the probe fails, the plugin shows `degraded` with the probe's last exit.
- **Plugins from Settings.** Open Settings and press `settings.nav.plugins`. Run `bridge type '{"target":{"key":"settings.plugins.source"},"text":"<P>/audit-probe"}'` and press `settings.plugins.install` ("Install Plugin"): `settings.plugin.audit-probe` appears and `./attn plugin list` agrees. Type `5` in `settings.plugin.audit-probe.priority`, named `audit-probe priority`, and press Enter: `priority` is 5. Press `settings.plugin.audit-probe.remove`: the card goes and `./attn plugin list` no longer holds `audit-probe`. `settings.plugins.browse` opens the system file dialog, which you cannot drive on a shared Mac.
- **Plugin input.** Run `scripts/verify-plugin-run-input.sh` for daemon wire and CLI stack proof on isolated data. The checks cover arbitrary harness IDs, both voices, permission-safe delivery, compaction outcomes, old API 7 payloads, terminal-only input, disconnects, daemon restarts, both PTY runtimes, retired reports, and a database from before input routes were recorded. Human keystrokes still reach the terminal. A direct run whose driver is unavailable defers automated input.
- **A plugin author's harness.** Run `scripts/verify-plugin-author-sdk.sh`. It packs the SDK into a tarball, copies `examples/plugins/sample-harness` to a clean folder with a new harness ID, installs it with `attn plugin install --path`, starts it in the picker's place, sends annotation and `attn agent msg` input, restarts the daemon, reloads the session and checks that models, which the sample leaves out, are unavailable. The guide page is `docs/guide/reference/writing-harness-plugins.md`.
- **A plugin harness's tools.** Drive them in [agent-tools.md](agent-tools.md).
- **A shared-server plugin.** Run `scripts/verify-plugin-server.sh`. It packs the SDK from the checkout, installs `examples/plugins/sample-server` with an arbitrary ID in an isolated stack, reuses an external server, discovers models and targets, checks both voices and duplicate IDs, resolves shell tools through the Go and Rust CLIs, and restarts the plugin and daemon with live and zero-view sessions. Missing registrations defer direct input. Active owners refuse uninstall. Aliases share one startup, control connection and status watch. Uninstalling the initiating alias and restarting the daemon keeps the surviving alias and physical server PID. Plain-shell calls make no catalog request, and conflicting root variables refuse caller-dependent commands.
- **Sigma, protocol 1 refused.** With no Sigma session open and no server on the instance's Sigma home, start `sigma serve` from a SolenesInc/sigma build before 43ebbba with `SIGMA_HOME` set to that home, and keep its pid. A `harness_models` request with `refresh` and a new Sigma session both fail with the refusal naming that pid. Stop that pid, and the next request starts a current server.
- **Sigma.** Build `sigma` from SolenesInc/sigma's main (`bun install && bun run build` in the checkout, or the checkout's own build script) and put it on the instance's login PATH or set `./attn settings set sigma_executable <path>`. With no plugin installed, `harness_catalog` reports Sigma `offered: false` until `./attn settings set sigma_enabled true`, then `offered: true` and `installation: "installed"`; ⌘N then names Sigma in the "Session agent" group. The env file gives Sigma `$ATTN_TOOL_HOME/.sigma` as its home, and the daemon log's `sigma: started … for <home>` line names it. Start a session with a short prompt and see it run and settle, `attn agent msg` it and see the message arrive as a follow-up. While a run works, send it an annotation and see the annotation reach the run before it ends; an agent message still waits for the run's end, as for every harness. Run `attn agent close --self -m "<reason>" --compact` from inside the agent and see the session close once its run ends. Run `attn delegate --agent sigma --role <a role that needs attn-workflow>`, see it return with a first turn and no `first_turn_unconfirmed`, and check `attn-workflow` under each folder `using-sigma` lists. A Sigma automation whose definition names a provider Sigma lacks fails before its first turn with Sigma's screen, and is never `delivered`. Run `attn seed note` from inside the agent and check the note's author is its session. Type `/fork` and a short prompt in the tile and see the tile move to a new session (the daemon log's `moved on from session`), its transcript follow the fork (including inherited history up to the fork), its usage and title start at the fork, and the old session hidden with its transcript unchanged. With `agent_tools_enabled` on, drive Sigma's tool calls in [agent-tools.md](agent-tools.md). After a run that edits a markdown file, read `./attn session transcript <id>` and `./attn agent peek <id>` for the prompt, the tool calls and the last reply, see the session titled from the prompt you typed, its usage in the session's details, the file in recent files, its activity line with activity on, and its replies offered when you select agent text to annotate. With headless tasks on and neither `claude` nor `codex` on the login PATH, see the Sigma session titled, its stop classified (the daemon log's `classifier: calling sigma`), `harness_catalog` report Sigma `options.one_shot: true`, the activity line written with `activity.config` `{"agent":"sigma"}`, and a paired sender's `attn model call` with `"harness":"sigma"` answered; `./attn session list` and Sigma's `conversation/list` show no conversation for those calls. On a Sigma home whose bundled `openai` has no sign-in and another provider is signed in (verify-sigma's `drive.ts up --fake-openai` gives a fake ChatGPT; copy its sign-in to `auth/<provider>.json` under a `[providers.<provider>] driver = "openai"`), the same title, stop verdict and `"tier":"light"` call go to that provider's light model, and `./attn settings set activity.config '{"agent":"sigma","model":"openai/gpt-6-luna"}'` is refused. In the native app, Settings → Agents shows a Sigma card with `settings.setting.sigma_executable`, a default route and no context cap; the Chief's setup offers Sigma while it is on; a Sigma session's palette has no context cap; the sidebar row shows Sigma's mark with harness logos on; the automation form offers Sigma. ## Contexts

- **Durability across restarts**: installed plugins start again with the daemon, and the daemon hands a reconnecting driver its own runs. A run keeps its input route even when its plugin is absent. Older runs wait for their owning driver to register before choosing a route. Harness settings are kept.
- **Linux**: plugins run where the daemon runs.
- **Outposts**: a harness's executable is a machine setting, so each outpost decides its own. The rest of the harness settings come from the home. A plugin agent launches on an outpost only under the plugin the home planned it with; when another plugin registers that agent there, the launch is refused with the plugin that does.
- **Profiles**: harness settings and plugins apply across all profiles on the daemon.
- **Performance and idle cost**: a plugin whose socket stalls does not stall the daemon. One shared Codex app-server uses less memory than a Codex per terminal ([shared-codex.md](shared-codex.md)).
- **Harnesses**: Claude Code reports through hooks and its terminal title. Codex reports through hooks, or through its app-server under shared Codex. A plugin harness reports through its plugin's driver. YOLO and the chief toggle each show only for the harnesses that support them.
- **Keyboard and native input**: ⌥1 to ⌥9 and ⌥T pick the harness in the picker. The palette toggles the logos.
- **Compatibility across versions**: a plugin names the API it was built for in its `attn-plugin.toml` (`attn_api_version`), and a driver older than the current input rules can still report input it took.

## Gotchas

- `auto_approve_enabled` and `sidebar_harness_logos_enabled` cannot be set back to empty: `""` is refused as an invalid boolean. Set `true`, their default.
- Close Settings before opening the palette: while Settings is open, the palette shortcut leaves its command field unfocused.
- The baseline's `ATTN_CLAUDE_EXECUTABLE` and `ATTN_CODEX_EXECUTABLE` win over the executables set in Settings, so changing one there changes nothing on the baseline.
- The mock stands in for `claude` and `codex` only. The shared-conversation warning needs two harness processes on one conversation, which the scenarios set up.
- `attn plugin` has no help. With no subcommand it prints its usage and exits 1, and `attn plugin --help` exits 1 with `unknown plugin command: --help`. Every subcommand prints JSON, and `uninstall` and `remove` do the same thing, `remove` adding `plugin_dir` to its reply.
- A shared-server plugin refuses uninstall while it owns any open server session, including a session with no view. Its declaration stays usable through a plugin disconnect; after a daemon restart, the session waits for the same owner to register again.
- A plugin that owns running delegated agents refuses to uninstall: `plugin "<name>" owns N active delegated run(s)`.
- Working but wrong: `attn plugin` has no help and always answers in JSON, and its `uninstall` and `remove` are two names for one action.
