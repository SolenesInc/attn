# Plan: code mode

Status: design and spike, on the `spike/tendril` branch, not for merge.

## Summary

Today an agent works attn one command per turn: plant a seed, read its id
back out of prose, note it, plant the next. Code mode lets the agent write one
Go program that calls attn's tools as typed Go functions. The program can
loop, branch, handle errors, and fan out in parallel, and it prints only what
the agent needs:

```sh
attn code <<'EOF'
package main

import (
	"attn"
	"fmt"
	"log"

	"golang.org/x/sync/errgroup"
)

func main() {
	titles := []string{"Fix login redirect", "Add request metrics", "Document code mode"}
	planted := make([]attn.Seed, len(titles))
	var g errgroup.Group
	for i, title := range titles {
		g.Go(func() error {
			s, err := attn.Plant(title, attn.PlantOptions{Body: "Found while triaging."})
			if err != nil {
				return fmt.Errorf("plant %q: %w", title, err)
			}
			planted[i] = s
			return attn.AddNote(s.ID, "triaged by code mode")
		})
	}
	if err := g.Wait(); err != nil {
		log.Fatal(err)
	}
	if _, err := attn.Tend(planted[0].ID); err != nil {
		log.Fatal(err)
	}
	for _, s := range planted {
		fmt.Println(s.ID, s.Title)
	}
}
EOF
```

A wire test runs this kind of program against a real daemon (see Spike
results).

Three choices carry the design:

- **The language is Go.** Every program is a valid Go program. Agents write
  Go fluently, and so does attn's maintainer. Go's own `go/parser` and
  `go/types` are the front end, so type errors are Go's messages, at the
  program's lines, before anything runs.
- **The schema is a Go package.** One file, `internal/codemode/api/attn.go`,
  declares the tools as Go: types with documented fields, and functions
  without bodies. The same file is what the agent reads, what the type
  checker enforces, and what the implementations are checked against.
- **It runs in the `attn` CLI process, as the calling session.** Each tool is
  a call through `internal/client`, so code mode has exactly the authority of
  the commands it replaces, and needs no protocol change.

The interpreter is a new package, `internal/tendril`: a sandboxed, metered
runtime for a large subset of Go. It adds no dependencies.

## The schema

### One declaration, four uses

`api/attn.go` is ordinary Go with bodiless functions:

```go
// A Seed is a ticket in the garden.
type Seed struct {
	ID    string
	Title string
	Body  string
	// State is planted, growing, parked, harvested or withered.
	State string
	// Tender is the session or crew member that claims the seed, or "" when
	// nobody does.
	Tender string
	Plot   string
	Ready  bool
}

// Plant creates a seed in the garden and returns it.
func Plant(title string, opts PlantOptions) (Seed, error)

// Show returns a seed and the latest notes in its log, oldest first.
func Show(id string) (Seed, []Note, error)
```

1. **Agents read it.** `attn code api` prints the package. `attn code api
   Plant Seed` prints one declaration with its doc, like `go doc`.
2. **The type checker enforces it.** Programs are checked against the package
   that this source declares, so a wrong call fails before the program runs:
   `main.go:6:20: cannot use 42 (untyped int constant) as string value in
   argument to attn.Tend`.
3. **The bindings are checked against it.** Each function and type is bound
   to a Go implementation in `tools.go`. Building the environment fails if
   anything is unbound or bound to something else. It also fails if a
   function's signature differs, or if a struct field has no counterpart of
   the identical type. So the schema cannot drift from the implementation,
   and a unit test catches a mismatch in CI.
4. **Editors and the real toolchain accept it.** `attn code stub` prints the
   package with `panic` bodies, so it compiles as real Go. A test builds a
   module from the stub and a program. `go vet` accepts the same program code
   mode accepts and rejects the same mistakes.

### Rules for tools

- **Arguments.** Required inputs are parameters. Optional inputs go in one
  `XOptions` struct, whose zero value means the defaults.
- **Results.** Results are typed structs, with `error` last. A tool never
  returns prose for the agent to parse.
- **Identity.** Every tool acts as the calling session. `attn.Me()` returns
  its id. No tool takes a session argument that would let it act as another
  session.
- **Vocabulary.** Names and values use the glossary. The facade translates
  legacy wire names, so a seed the wire calls `dormant` is `parked` in code
  mode.
- **Concurrency.** Tools are safe to call from many goroutines. Their calls
  run in parallel (see Execution).
- **Compatibility.** Like the protocol, the package grows by addition. A
  rename or a changed signature breaks programs agents have learned, so it is
  a deliberate decision.

### Why not the other schemas

- **Generated from `main.tsp`.** The wire types serve the wire: pointers for
  optional fields, scoping fields the client injects, and legacy names. A
  generator could later produce the result structs, but the agent-facing
  shape is curated.
- **JSON Schema per tool, as MCP does.** Code mode replaces many tool schemas
  with one typed package. If attn ever offers code mode over MCP, it is one
  tool, `run(program)`, and the package text is that tool's description.

## Execution

- **Where.** `attn code` compiles and runs the program in the CLI process.
  - The tools call the daemon through `internal/client`, which keeps every
    handler check in force: garden scoping, `requireHome`, and the
    terminal-to-session identity.
  - The daemon gains no state and no memory, and an interpreter bug cannot
    crash it.
  - On an outpost, Garden calls fail at the existing home-only fence, as the
    commands do.
- **Entry and output.**
  - A program is `package main` with `func main()`.
  - stdout gets `fmt.Print*` and `os.Stdout`.
  - stderr gets `log`, `println` and `os.Stderr`.
  - The exit status is 2 for compile errors and 1 for runtime errors. Programs
    set it themselves with `os.Exit` or `log.Fatal`.
- **Limits.** Each run gets 50M fuel and 256 MB of allocation, a call depth of
  1000, and 64 goroutines. Ctrl-C cancels it.
- **Parallelism.**
  - Goroutines run one at a time on the interpreter, which keeps metering
    deterministic and lock-free.
  - A tool call releases the interpreter while it waits, so calls from
    separate goroutines overlap. Eight 100 ms calls fanned out with errgroup
    finish in 101 ms.
- **Cost.** About 3 ms to build the environment and 0.3 ms to compile a
  program, per invocation.

## The language

Code mode accepts Go. The subset is large. The conformance suite runs 13
programs through both `go run` and tendril, and requires byte-identical
output. Together they cover everything below.

Supported:

- **Types.** Every integer and float kind, strings, booleans, slices, arrays,
  maps with any comparable key, structs, and pointers to anything. Also
  functions and closures, interfaces, and channels.
- **Declarations.** Methods with value and pointer receivers; embedding, with
  promoted fields and methods; and generic functions and types, with
  constraints.
- **Expressions.** Method values and method expressions, type assertions and
  type switches, and `iota` constants.
- **Statements.**
  - All `for` and `range` forms, including range over int, channels and
    iterator functions.
  - `switch` with `fallthrough`, and labeled `break` and `continue`.
  - `defer`, and `recover` with Go's rule that only a function deferred
    directly can recover.
- **Concurrency.** Goroutines, buffered and unbuffered channels, `select` with
  `default`, `close`, and range over a channel.
- **Standard library subset.**
  - Text: `fmt` (`Print*`, `Sprint*`, `Fprint*`, `Errorf` with `%w`), `strings`
    (including `Builder` and the iterator functions), `strconv`, `regexp` and
    `path`.
  - Values and errors: `errors`, `math` and `cmp`.
  - Collections: `slices`, `maps`, `iter` and `sort`.
  - Concurrency: `sync` (`WaitGroup` with `Go`, `Mutex`, `RWMutex`, `Once`) and
    `golang.org/x/sync/errgroup`.
  - Program edges: `time` (`Duration`, `Sleep`), `log`, `os` (`Stdout`,
    `Stderr`, `Exit`), `io.Writer` and `encoding/json` (tags, `omitempty`,
    embedding, `MarshalIndent`, `Unmarshal`).

Refused at compile time, with a positioned message:

- `goto`;
- complex numbers;
- anything outside the list above, such as `os.ReadFile`, `net` or `unsafe`.

Deviations from Go, each deliberate:

- **Map order.** Ranging over a map visits keys in sorted order. Sorted is one
  of the orders Go permits, so programs stay correct Go, and runs repeat
  exactly.
- **Pointer printing.** A nested pointer prints as `&{...}`, not as an
  address.
- **Error wording.** `encoding/json` type errors say the same thing as Go's,
  in different words.

## Sandbox guarantees

The interpreter enforces these whatever the program does. Each one has a test.

- **No ambient authority.** A program reaches only the declared packages. It
  has no file system, network, environment, reflection or `unsafe`.
- **Bounded.**
  - Fuel counts statements, loop iterations, calls, and work proportional to
    the input of builtins and tools.
  - The allocation budget covers values, strings, maps, channels, goroutines
    and output.
  - Call depth guards the Go stack, whose overflow could not be recovered.
  - The caller's context covers wall time.
  - A goroutine spinning in a loop is preempted at fuel checkpoints, so it
    cannot starve the others.
- **Halts cannot be swallowed.** `recover` catches panics and runtime errors
  but never an exhausted limit. A halt raised inside a `String` or `Error`
  method that `fmt` calls also stays tripped, even though `fmt` recovers
  panics.
- **Contained.**
  - Runtime errors and tool panics come back as errors at the program's line,
    for example `main.go:14:2: runtime error: index out of range [5] with
    length 2`.
  - A deadlock is reported the way Go reports it.
  - Exceeding the goroutine limit fails the run.
  - When a run ends, every goroutine it started has exited. Tests check this
    with `runtime.NumGoroutine`.
- **Isolated.** Values are copied in and out. A program's globals are fresh
  on every run.
- **Durable when asked.** A tool package marked `Journaled` records its
  results. `Resume` replays them, so a resumed program does not redo finished
  calls, and an edited program fails with `ErrDiverged`. Code mode does not
  use this today. It is there for automations or orchestration.

## Spike results

Measured on a 4-vCPU Xeon at 2.8 GHz with Go 1.27.1. Everything below passes,
including under `-race`.

- **Conformance.** 13 programs, compared byte for byte with `go run`.
- **Sandbox.** 16 hostile scripts and 11 concurrency failures: deadlocks,
  goroutine bombs, spinning goroutines, panicking workers, misuse of closed
  channels and unlocked mutexes, and halts inside methods `fmt` calls.
- **End to end.**
  - `internal/daemon/codemode_wire_test.go` runs the triage program above
    through a real daemon. It plants three seeds in parallel, notes them,
    tends one, parks one, lists the garden and reads a log.
  - It then checks the garden through the ordinary client.
  - The run cost 78 fuel.
- **Real toolchain.** The stub plus a program passes `go vet`, and both
  checkers reject the same typo.

Performance against goja, the JavaScript engine attn already ships:

| Workload | tendril | goja |
|---|---|---|
| `fib(20)` | 1.6 ms | 4.1 ms |
| 100k-iteration loop | 13.7 ms | 26 ms |
| word count over 3.7 KB | 0.61 ms | 1.8 ms |
| stripped binary over a 1.5 MB baseline | +4.0 MB | +8.9 MB |

Ints larger than 255 are boxed in `any`, which costs 233k allocations in the
loop. Typed closures would remove that; it is the next performance step.

## Landing

1. **Tendril and `attn code`, behind an experimental setting, off by default.**
   - The skill documents code mode only when the setting is on.
   - Prompt changes follow the prompt-authoring workflow.
2. **One implementation per tool.**
   - Fill the `attn` package to cover the roughly 55 agent-facing command
     forms: garden, delegation, agents and inbox, sessions, PRs and present.
   - Refactor each CLI command into flag parsing over the same Go function
     the package binds. The CLI and code mode then share one implementation,
     and the command help can come from the package docs.
3. **Typed closures and differential fuzzing.** Generate Go programs and
   compare tendril with `go run`.
4. **Reuse.** Tendril can later run automation gates and, if attn keeps
   orchestration, replace the goja workflow engine. The journal and resume
   are ready for that.

## Decisions needed

- **Where programs run.** Proposed: the CLI process. Running in the daemon
  would mean a new protocol command and interpreter memory in the daemon.
- **Where the schema comes from.** Proposed: a curated, hand-written package.
  The alternative is generating it from `main.tsp`.
- **The import path.** Proposed: `attn`, which is short. It could also be a
  full module path.
- **The interpreter's name.** `tendril` is a placeholder.

## Alternatives for the language

| Option | Why not |
|---|---|
| Compile with the real Go toolchain | It needs the toolchain on every machine. It can't be sandboxed or metered, and builds take seconds. |
| Yaegi | Interprets Go, but it is not a sandbox: no metering, real goroutines, and stdlib that reaches the host. |
| goja (JavaScript) | Already a dependency, but needs determinism bans, has no memory limit, adds 9 MB and lacks static types. |
| Starlark | A proven sandbox, but Python-flavored, dynamically typed, and a new dependency. |
| expr, CEL | Expressions only. |
| Wasm | The strongest isolation, but it needs an ahead-of-time compiler, so it is not dynamic. |
