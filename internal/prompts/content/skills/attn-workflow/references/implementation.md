# Implementation

Principles this process relies on: [Prove it works](../principles/prove-it-works.md), [Sequence verifiable units](../principles/sequence-verifiable-units.md), [Build the lever](../principles/build-the-lever.md), [Smallest change](../principles/smallest-change.md), [Test behavior, not implementation](../principles/test-behavior-not-implementation.md), [Attack the premise](../principles/attack-the-premise.md), [Never block on the user](../principles/never-block-on-the-user.md), [Update what a decision overturns](../principles/update-what-a-decision-overturns.md), [Guard the context window](../principles/guard-the-context-window.md), [Match rigor to consequences](../principles/match-rigor-to-consequences.md), [Refactor first](../principles/refactor-first.md), [Parse, don't validate](../principles/parse-dont-validate.md), [Derived things must earn their place](../principles/derived-things-must-earn-their-place.md). Read them before you start; [the skill's index](../SKILL.md#principles) lists the rest.

Read the agreed brief or plan and inspect the relevant code before editing. Make the change fit the codebase and resolve routine implementation choices yourself.

The plan's findings record what spikes and investigation already established. Build on them rather than rediscovering them. When the code appears to contradict a finding, or a simpler route appears than a finding allows, treat it as an unforeseen issue below instead of working around the finding.

A change that turns out to need a parallel version of an existing mechanism, which the plan did not account for, is an unforeseen issue. So is a departure from the plan's Design, such as a parameter, type or owner it did not anticipate: decide whether the design was wrong, a requirement was missed, or the implementation is overreaching, instead of absorbing the difference silently. When an unforeseen issue requires a consequential decision, bring the evidence, what you tried, and your recommendation to the coordinating agent identified in the brief, or to the user if none is identified. Continue independent work while waiting; wait before proceeding with work that depends on that decision.

Verify the affected behavior as [Prove it works](../principles/prove-it-works.md) and [Sequence verifiable units](../principles/sequence-verifiable-units.md) describe: each unit ends in a check you ran on the surface the change touches, following the repository's verification guidance. When the repository has a `drive-*` skill, read the files of the features the change touches, update them in the same change when it adds, removes or alters a way in, and check every way in and context they list that applies before you call the change done. Reuse evidence that still applies and run further checks where changes or gaps warrant them. Address review findings, including rejected seed checks, whose verdict says what would prove them, then verify the corrections. When two corrections that shared an assumption have failed the same check, [Attack the premise](../principles/attack-the-premise.md) before writing a third.

Report each check on the seed as you prove it, with the commit it ran on. `attn seed show <seed-id>` lists your seed's checks, the plot's shared ones included. A local file passed to `--evidence` is copied onto the seed and cited in the same call. The first line of `-m` is the summary line; put what a reviewer needs beyond it on the lines after:

```sh
attn seed check report <seed-id> <C#> -m "<summary line>" --evidence <file|artifact|url> --commit <rev>
```

A check that does not apply still gets a report: say why and cite what shows it, and the verdict decides. A later run is a new report. It replaces the earlier one and clears its verdict, so the seed always shows which evidence is current. Cite the new evidence under the same name to replace the earlier file, or under a new name when the plan or notes cite the earlier one. When the brief numbers checks that are not on the seed, report each one in a note with its evidence.

Return a reviewable change with the revision, each check with the current evidence that proves it, how to rerun the checks, and remaining limits. Make the result readable in the conversation and durable in the seed. Deliver as [Delivery](delivery.md) describes, within the task's authorization.
