# Implementation

Principles this process relies on: [Prove it works](../principles/prove-it-works.md), [Sequence verifiable units](../principles/sequence-verifiable-units.md), [Build the lever](../principles/build-the-lever.md), [Smallest change](../principles/smallest-change.md), [Test behavior, not implementation](../principles/test-behavior-not-implementation.md), [Attack the premise](../principles/attack-the-premise.md), [Never block on the user](../principles/never-block-on-the-user.md), [Update what a decision overturns](../principles/update-what-a-decision-overturns.md), [Guard the context window](../principles/guard-the-context-window.md), [Match rigor to consequences](../principles/match-rigor-to-consequences.md), [Refactor first](../principles/refactor-first.md), [Parse, don't validate](../principles/parse-dont-validate.md), [Derived things must earn their place](../principles/derived-things-must-earn-their-place.md). Read them before you start. [The skill's index](../SKILL.md#principles) lists the rest.

Read the agreed brief or plan and inspect the relevant code before you edit. Make the change fit the codebase, and resolve routine implementation choices yourself.

The plan's findings record what spikes and investigation already established. Build on the findings instead of rediscovering them. When the code appears to contradict a finding, or you see a simpler route than a finding allows, treat the case as an unforeseen issue, described below, instead of working around the finding.

A change that turns out to need a parallel version of an existing mechanism, which the plan did not account for, is an unforeseen issue. So is a departure from the plan's Design, such as a parameter, type, or owner the plan did not anticipate. For such a departure, decide whether the design was wrong, a requirement was missed, or the implementation is overreaching. Do not absorb the difference silently. When an unforeseen issue requires a consequential decision, bring the evidence, what you tried, and your recommendation to the coordinating agent identified in the brief, or to the user if the brief identifies none. Continue independent work while you wait. Wait for the decision before you proceed with work that depends on it.

Verify the affected behavior as [Prove it works](../principles/prove-it-works.md) and [Sequence verifiable units](../principles/sequence-verifiable-units.md) describe. End each unit with a check that you ran on the surface the change touches, following the repository's verification guidance. When the repository has a `drive-*` skill, read the files of the features the change touches. When the change adds, removes, or alters a way in, update those files in the same change. Before you call the change done, check every applicable way in and context that the files list. Reuse evidence that still applies, and run further checks where changes or gaps warrant them. Address review findings, including rejected seed checks, whose verdict says what would prove them. Then verify the corrections. If two corrections that shared an assumption have failed the same check, [Attack the premise](../principles/attack-the-premise.md) before you write a third.

Report each check on the seed as you prove it, with the commit the check ran on. `attn seed show <seed-id>` lists your seed's checks, the plot's shared checks included. attn copies a local file passed to `--evidence` onto the seed and cites it in the same call. The first line of `-m` is the summary line. Put what a reviewer needs beyond the summary on the lines after it:

```sh
attn seed check report <seed-id> <C#> -m "<summary line>" --evidence <file|artifact|url> --commit <rev>
```

Report a check that does not apply too. Say why, and cite what shows it. The reviewer then rules on the check. Each later run is a new report. The new report replaces the earlier report and clears its verdict, so the seed always shows which evidence is current. To replace the earlier file, cite the new evidence under the same name. When the plan or notes cite the earlier file, cite the new evidence under a new name instead. When the brief numbers checks that are not on the seed, report each of them in a note with its evidence.

Return a reviewable change. Include the revision, each check with the current evidence that proves it, how to rerun the checks, and the remaining limits. Report the result in the conversation and record it in the seed. Deliver as [Delivery](delivery.md) describes, within the task's authorization.
