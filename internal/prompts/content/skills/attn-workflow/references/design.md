# Design

Principles this process relies on: [Model the domain first](../principles/model-the-domain-first.md), [Parse, don't validate](../principles/parse-dont-validate.md), [Minimize reader load](../principles/minimize-reader-load.md), [Separate before serializing shared state](../principles/separate-before-serializing-shared-state.md), [Refactor first](../principles/refactor-first.md), [Migrate callers, then delete the old way](../principles/migrate-callers-then-delete-the-old-way.md), [Match rigor to consequences](../principles/match-rigor-to-consequences.md). Read them before you start. [The skill's index](../SKILL.md#principles) lists the rest.

Use this reference to shape, compare, or review an interface, and the structure behind it: any boundary through which people, agents, or other code use what you build, such as a function, type, module, package, command line, file format, protocol, or web API. The checks are the same inside a codebase and across organizations. What changes is the cost of a mistake, which grows with the number of callers and with how hard they are to change.

## Start from the caller

Write the calling code before the interface. Pick two or three realistic call sites: the common case, a demanding case, and a call that should fail. Judge a design by how those call sites read, not by how convenient the implementation is. When comparing designs, write the same call sites against each and read them side by side. (Bloch: "Code the use-cases against your API before you implement it"; Muratori: write the usage code first.)

## Checks

Apply each check to the call sites. Skip a check that does not fit the interface rather than forcing it. The sources in parentheses give the fuller argument.

- **Deep, not shallow.** Count the parameters and concepts a caller must handle against what the implementation hides. The caller's count should be much smaller. A layer whose signature is as wide as the thing it wraps adds a concept without removing a concept. Pull complexity down into the implementation instead of pushing it onto every caller. (Ousterhout, *A Philosophy of Software Design*)
- **Hide the decisions likely to change.** Each module owns a design decision that callers cannot observe, so the decision can change without them. (Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules")
- **Common case short, rare case possible.** In the typical call, the caller states only what is essential and takes defaults for the rest. Full control stays reachable through the same interface. (Bloch: "easy to do simple things; possible to do complex things")
- **Hard to misuse.** Prefer designs in which a wrong call cannot be written: types that carry the invariant, distinct types for values that must not mix, required arguments instead of rules about call order. When misuse is detectable only at runtime, fail at the first point where it is detectable. (Bloch: "Fail fast… Compile-time is best"; [Parse, don't validate](../principles/parse-dont-validate.md))
- **Useful from the start.** A new value works without a setup step. If callers must remember an initialization step, some will forget it. (Go proverb: "Make the zero value useful")
- **Define errors out of existence.** Redefine an operation so the edge case is ordinary: removing something absent succeeds, a range past the end is clamped. Make each remaining error name what failed, the value or limit involved, and what the caller can do. Whoever fixes the call, a person or an agent, often sees only the message. (Ousterhout; Bloch, *Effective Java*: "Include failure-capture information in detail messages")
- **Small pieces that compose.** Narrow interfaces that combine are better than a broad interface that anticipates every combination. Small interfaces and uniform data at the boundary let unrelated parts work together. (The Unix philosophy; Go's `io.Reader` and `io.Writer`)
- **Keep concerns apart.** Can a caller change when, where, or by whom something runs without changing what it does? If not, the interface couples those choices, and callers must accept all of them to get one. (After Hickey, "Simple Made Easy")
- **When in doubt, leave it out.** Every element is a promise. You can add to an interface later, but you cannot take anything away. (Bloch)
- **Names that explain.** Read each call site aloud. If a call site needs a comment to say what it does, rename the names it uses. If no clear name comes, move the boundary. Give the same concept the same name everywhere, and give opposite operations named pairs. (Bloch: "Strive for intelligibility, consistency, and symmetry")
- **One mechanism per job.** List the existing interfaces that already do this job, found by what they do rather than by name. Extend or unify them before you add another. Two ways to do one thing double every later change. ([Refactor first](../principles/refactor-first.md))
- **Consistent with its neighbors.** Follow the conventions of the surrounding code and ecosystem, even where a local variation would be slightly better. Callers carry what they learned from one interface to the next.
- **A small vocabulary with a validator, where uses are many.** When people or agents will write many uses in a bounded domain, give them a small, constrained vocabulary, such as typed builders, an internal DSL, or a schema, backed by a deterministic checker whose errors point to the fix. An author can then write a candidate, check it, and repair it unaided. The vocabulary costs a language to design and maintain. It is worth that cost only while the domain is truly bounded and the vocabulary stays small. (Joshi, "DSLs Enable Reliable Use of LLMs", martinfowler.com, 2026)
- **Evolves without breaking callers.** Name the likeliest next requirement and show what changes at the call sites. Do not build for it. Check only that it would be additive. If existing callers would have to change, reconsider the boundary. With enough callers, every observable behavior is depended on, whatever the contract says, so changing any observable behavior is a break. (Hyrum's law, *Software Engineering at Google*; Torvalds: "we don't break userspace")

## Check the structure behind it

A boundary is judged from outside, by its call sites. The structure behind it is judged by the next person to change it, often an agent that sees only the files it opened, copies the nearest example, and takes the shortest path that compiles. Prefer the structure in which a change that looks right from one file is right for the whole system.

- **Data structures first.** Trace each common access pattern through the proposed types. If a pattern needs a map, index, or cache added later to be fast or correct, the structure is wrong now.
- **One writer per piece of state.** When two modules write the same state, or each keeps its own copy, someone who edits one writer cannot see the others, and the writers' rules drift apart. Give the state one owner. Other modules read the state or ask the owner to change it. When two actors genuinely write at the same time, give each its own state and combine them where they are read.
- **Organized by knowledge, not by order of execution.** Separate load, validate, transform, and save modules repeat one representation and its rules across every boundary between them. Group code by the decision it protects. Code that runs at different times can share a module. (Ousterhout: temporal decomposition)
- **One list.** When adding an item means editing several lists, an agent that finds one list updates only that one. Keep one list and derive the others. When a list cannot be derived, make the build fail when the lists disagree.
- **Internals out of reach.** Code that can import a module's internals will import them, and the internals become part of the module's interface. Make the internals unreachable, so an import from outside fails the build. Use an unexported name, an `internal` directory, or an import test.

## Weigh the result

The checks conflict with each other: a deep module against small composable ones, a constrained vocabulary against a general one. Match the effort to the interface's reach, as [Match rigor to consequences](../principles/match-rigor-to-consequences.md) describes. A private helper with one caller needs a good name and little else. A boundary that many callers or other teams depend on needs the full pass. Prefer the design whose call sites read clearly with the fewest concepts and whose structure leaves the next change one obvious place to go, and say which checks decided it.
