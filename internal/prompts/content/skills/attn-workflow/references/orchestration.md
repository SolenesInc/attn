# Orchestration

Own execution of the agreed plan. Read the plan in the seed and inspect enough relevant code to prepare useful assignments. Use settled design decisions; what goes back to the user, and how, is under Questions for the user.

Delegate implementation where a cheaper model can carry it out reliably. Make small changes directly when delegation would cost more effort than it saves.

Write each Builder's brief as `attn seed guide` describes under WRITING A BODY, with the plan's seed, the code location, the decisions and findings that constrain the work, and the completion checks it cites. Identify yourself and provide your contact as the point of contact for unforeseen issues requiring advice. Specify progress checkpoints when useful for the assignment.

After delegating, wait for updates. Updates may report completion, a progress checkpoint, or a question needing advice. Use those updates to decide when to inspect code, answer questions, review results, or adjust assignments. Avoid following every implementation step in parallel with Builder. The brief is the standing record of the assignment: when you redirect a Builder, change its brief first, then message it, because a resumed or replacement Builder reads the brief, not your earlier messages.

When advising, read the relevant code and evidence and ask follow-up questions as needed. Help resolve the issue and keep the plan current when decisions change or a finding is overturned. If an assignment stalls, reassess the brief and model choice before repeating the same approach. When two of a Builder's fixes that shared an assumption have failed the same check, attack the premise as the skill's engineering judgment describes before approving a third. When you correct Builders for the same kind of mistake twice, fix the class: in this plan's briefs when it is specific to the plan, and with [Correction](correction.md) when it lives in the repository, planting it as a seed when that work falls outside the agreed plan.

## Questions for the user

The user reads your question cold, between other agents, and may answer hours later. Before asking, classify the question. A fact that running something would settle, such as behavior, timing, layout or output, is not theirs to answer: run the check or a prototype and let the result decide. A reversible call inside the agreed scope is yours: decide it, record the decision in the plan, and report it with what the user could tell you to do instead. What reaches the user is a product or preference call no experiment settles, a change to the agreed scope or intent, or an irreversible step.

Record the question before asking it, as an open item under the plan's Decisions in the seed, in the shape [Planning](planning.md) gives open questions. Route work around it. Then ask so it can be answered without this conversation: one line saying how many things need the user, and for each question two lines, the decision with your recommendation and the reason, then what happens without an answer, with a link to the seed for the detail. Batch questions that arrive close together, ask each once, and do not repeat open questions in every progress update. Ask with `attn ask` when your launch guidance includes it, and keep working; the user answers from one place, and for a question about your stake the answer comes back as a note on the seed. Otherwise end your turn with the questions in the conversation. The content and the record are the same on either channel.

When the answer comes, write the decision and its reason into the plan's Decisions, rewrite every part of the plan that depends on it as [Planning](planning.md) describes under Tracking and handoff, record who decided it in a note, remove it from the open questions, and pass it to each Builder whose brief it changed. A question that work has overtaken is withdrawn the same way, with the note saying why.

Review each Builder's completed work against the plan yourself, completion check by completion check, from the evidence each check names. You did not write the Builder's code, so your review is the independent one; a change you make yourself has no independent review, and you say so when you report it. Check how the pieces work together and return needed corrections to the Builder. When the work grows a parallel mechanism beside an existing one, bring it to the user as a scope question rather than working around it. Evidence counts for the commit it ran on: after a new commit, rerun the checks the change could affect and reuse the rest, and run further checks when gaps or contradictions warrant them. Judge the overall outcome complete only when the evidence supports it.

Make the result readable in the conversation and durable in the seed. Follow the task's authorization for delivery steps.

For delegation commands, use the `attn` skill's delegation reference. Each new assignment gets its own seed referencing the plan. Choose the folder and checkout explicitly; record the returned seed and checkout so updates and advice use the right context.
