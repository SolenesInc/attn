# Experience first

Apply when product, interface, or scope tradeoffs come up.

Whoever consumes the work is its user: the person in the product, the code that calls the library, the agent that reads the error, and the next maintainer. When implementation convenience conflicts with their experience, choose their experience. Keep a feature, control, or option only when it serves the user. A few polished features beat many rough ones. Attend to the details: feedback, error states, and what the user sees while waiting. Settle a choice that depends on feel by [comparing options](compare-options-before-committing.md), not by argument. Say what changes for them before you describe the implementation.
